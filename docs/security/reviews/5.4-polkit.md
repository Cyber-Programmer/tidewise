### R-01 (Medium, CONFIRMED): the polkit test header claims a manual dialog check that was not done for this action
`tests/container/tests/polkit.rs:12-14` says "The dialog was checked by hand on a KDE agent (decision 0005, threat T-02)".

- No 5.4 entry exists in `docs/progress.md`.
- The stock action's message is `Authentication is needed to run \`$(cmdline_short)' as ...`, which pkexec sets via `polkit.message`. That key is set only for the stock action (pkexec.c, `action_id == "org.freedesktop.policykit.exec"`).
- For our action the dialog text is our own `<message>`. So the old check says nothing about our message.

Fix: reword the comment ("checked on the stock action only; own action re-test pending") or do the re-test first. Run it with the hostile argvs in A below and record the result.

### R-02 (Medium, PLAUSIBLE, from pkexec.c): the first token of `command_line` is attacker-chosen, and the helper ignores argv[0]
pkexec.c does `path = g_strdup(argv[n])`, resolves it, then `path_abs = g_strdup(path); argv[n] = path_abs;`, and later `command_line = g_strjoinv(" ", argv + n)`. Matching uses `realpath(path)` only.
- A same-user process can create a symlink such as `/tmp/<up to ~4 KB of text, newlines allowed>/x` pointing at `/usr/lib/tidewise/tidewise-helper`, then run `pkexec <symlink> "<true summary>"`.
- `exec.path` still matches, so our action and message are used.
- If `argv[n]` keeps the typed spelling when the path is absolute (the quote did not show the surrounding `if`), the dialog shows the Tidewise sentence, then attacker text, then the true summary. The helper accepts, because `summary_arg` in `args.rs:19-26` discards argv[0] (`_program_name`).
- Result: a genuine transaction (T-01 allows these) whose dialog frames the true summary with attacker prose. The summary itself stays last and intact.

Fix, helper side, in `args.rs` / `gate.rs`: require argv[0] to equal `/usr/lib/tidewise/tidewise-helper` byte for byte, and refuse otherwise (same coded error path as a mismatch). Then for every accepted request the whole `command_line` is fixed path + summary, and the dialog cannot be dressed up. Add a hostile-input test (red first). This touches `crates/helper*`, so it needs the human's OK.

### R-03 (Low, CONFIRMED): a refused (spoofed) call still shows a Tidewise-branded password prompt
Verified from source:
- `command_line` is not sanitised, escaped or truncated (pkexec.c). Only `cmdline_short` is cut, to 38 + " ... " + 37 characters.
- There is no limit on its length except argv size.
- `$(key)` expansion is single pass: values are appended to the output buffer and not rescanned, so a literal `$(user)` in argv stays literal. An unknown key stays literal and logs an error.
- I saw no escaping of the expanded message in the polkitd code I read. `sanitize_for_log` is applied only to log output.

Consequences:
- Any user process can run `pkexec /usr/lib/tidewise/tidewise-helper "<anything>"`. Because the fixed sentence comes first, it cannot be pushed out of view, but the text after it is free: newlines, very long text, `<b>`, `&`, "no password needed".
- If the user authenticates, polkit starts the helper as root. The helper refuses with `SummaryMismatch` and does nothing. The password goes to the agent, not to the attacker.
- This is a social-engineering and fatigue vector (T-02, T-16). It is not a privilege gain.

Unverified (could not read the agents' widget code):
- Whether the KDE agent renders markup. A Qt `QLabel` in AutoText mode renders rich text if the string looks like HTML. This is a known Qt behaviour; I could not confirm which text format this agent uses. This is the most important case to hand-test.
- What GTK agents do.
- A megabyte-sized argv could make the dialog unusable or push the buttons off screen.
- Invalid UTF-8 in argv goes into a D-Bus string. That is pre-existing polkit behaviour for every action, but worth one manual try.

Test on KDE and GNOME with: `<b>x</b>`, `&amp;`, 200 lines, 100 KB, `$(user)`, and a symlinked path as in R-02.

### R-04 (Low, CONFIRMED): the guard tests do not see code after the first `#[cfg(test)]`, or in subfolders
`file_changes.rs` (`found`) and `work_folder.rs` (`production_lines`) both do `text.split("#[cfg(test)]").next()`.
- Nothing asserts that `mod tests` is the last item of each file. A production `fn` appended after `mod tests { .. }` is invisible to both guards.
- `fs::read_dir(src)` is not recursive, so `src/sub/mod.rs` or `src/bin/x.rs` is never scanned.
- The lib.rs skip-list parser handles only `#[cfg(test)]` on its own line followed by `mod x;`. That fails safe, because anything it does not understand is scanned.
- Several checks are string matches that are easy to evade without any bad intent:
  - `work_folder.rs` `exactly_one_production_line_builds_a_workdir` looks for `WorkDir {`, but `Self { path }` or `WorkDir{` inside `impl WorkDir` is not matched.
  - `no_production_code_calls_workdir_open` matches `WorkDir::open(`, but `Self::open(` is not matched.
  - These two are backed by the compile-level defences, which are sound (see "Checked and found fine").
- The earlier-reported "cfg(test) early in a file" risk does not exist today: every `src/*.rs` file has exactly one standalone marker, and `workdir.rs` has two.

Fix:
- In each guard, assert that the text after the marker starts with `mod tests {` and that the file ends at that module's closing brace.
- Assert that `src/` has no subdirectories.
- Prefer clippy bans (D below) to string lists wherever possible.

### R-05 (Low, CONFIRMED): the clippy ban has gaps, and `file_changes.rs` WORDS does not cover them
`clippy.toml` bans only `Command::new`, `fs::remove_file`, `remove_dir`, `remove_dir_all`.

The helper depends on `rustix` with features `fs` and `process`, so these are available and banned by nothing:
- Direct deletion: `rustix::fs::unlink`, `unlinkat`, `rmdir`. The WORDS list contains `remove_file`, `remove_dir` and similar, and none of those substrings appear in these names.
- Replacing or destroying a file: `rustix::fs::rename`, `renameat`, `renameat_with`, `ftruncate`, `truncate`.
- Changing metadata or links: `chmod`, `fchmod`, `chown`, `fchown`, `link`, `symlink`, `mkdir`.

Other `std` routes not covered:
- `std::fs::hard_link`, `soft_link`.
- `std::os::unix::fs::{chown, lchown, fchown}`, `File::set_permissions`, `File::set_len`. `set_len` needs a writable open, which WORDS catches via `OpenOptions` / `File::create`. `File::set_permissions` is not caught.
- `File::options()`, the alias for `OpenOptions::new()`. It is not in WORDS, so `File::options().write(true).truncate(true).open(..)` passes both guards.
- `use std::fs::rename; rename(..)`. WORDS has `fs::rename`, so the bare imported form is missed.

Not a gap: `CommandExt::exec` and `Command::spawn` / `output` need a `Command`, which `Command::new` already bans. `rustix::runtime::execve` needs a feature that is off, and `unsafe` is forbidden.

Add to `disallowed-methods`, with a "single caller" reason:
- `std::fs::rename`, `std::fs::hard_link`, `std::fs::soft_link`
- `std::fs::File::options`, `std::fs::OpenOptions::new` (the only sites are `workdir.rs`, `create_new`, and tests)
- `std::fs::File::set_len`, `std::fs::File::set_permissions`, `std::fs::set_permissions`
- `std::os::unix::fs::{chown, lchown, fchown}`
- `rustix::fs::{unlink, unlinkat, rmdir, rename, renameat, renameat_with, ftruncate, truncate, chmod, fchmod, chown, fchown, link, linkat, symlink, symlinkat, mkdir, mkdirat}`

Where a legitimate use exists, expect it on one function. `std::fs::File::create` and `std::fs::write` could also be banned, since they truncate. They are already in WORDS, so this is optional.

Also consider asking the human whether the rustix `fs` feature can be dropped. The `umask` call is gated by `fs` in rustix, as the threat model notes, so it probably cannot.

### R-07 (Low, CONFIRMED): policy tests do not assert the absence of widening annotations or translations
`polkit_policy.rs` checks defaults, `exec.path`, no `allow_gui` / `exec.argv1` / `_keep`, and one `<message>`.
- It does not assert that `exec.path` is the only `<annotate>`. `org.freedesktop.policykit.imply`, `owner` and `exec.allow_gui` variants would not be caught, except `allow_gui` by substring.

### R-08 (Low, PLAUSIBLE): a path mismatch silently downgrades to the stock action
pkexec compares `realpath(argv[n])` exactly to `exec.path`. A miss falls back to `org.freedesktop.policykit.exec` (pkexec.c quote above).

Today the path is a constant in the policy; the app and PKGBUILD (5.5) must install and call exactly `/usr/lib/tidewise/tidewise-helper`. A packaging slip, or a different location such as `/usr/lib64` or a symlinked `/usr/lib`, would:
- show the stock dialog, with `cmdline_short` cut in the middle to 80 characters, which may hide the summary;
- use the stock action's default, which is `auth_admin_keep` on a stock Arch policy (I did not re-read the shipped file this session). That retention is the thing golden rule 6 avoids.

The fallback is still safe for the helper, because it re-checks everything and never trusts how it was authorised. But the UX and rule-6 properties silently change.

Fix: a test in 5.5 (the package) that the installed helper's `realpath` equals the annotation. Optionally the helper compares `/proc/self/exe`'s realpath with the constant and refuses otherwise, which together with R-02 closes this. Nothing in the container test exercises `find_action_for_path` (the container header says so honestly).

## Checked and found fine

- **`remove_work_file` path handling (C).**
  - `Path::file_name` returns `None` for `..`, an empty path and root.
  - `Path::parent` compares normalised components. Interior `.`, repeated slashes and a trailing slash or `/.` normalise to the same parent. Such spellings reach the same real file, and the target is rebuilt as `dir.path().join(name)`. `name` is a single Normal component, so it cannot contain `/`.
  - `work/sub/../f` has parent `work/sub/..`, not `work`, so it is refused. This is tested.
  - Non-UTF-8 names are fine: `OsStr` is used throughout.
  - Only the final component is checked with `symlink_metadata`, and only the final component is unlinked. `unlink` never follows a symlink and fails on a directory (`EISDIR`). So the TOCTOU between `symlink_metadata` and `remove_file` cannot redirect the deletion. At worst the swap makes the removal fail. A hard link only loses one name.
  - The folder's own path in production is the constant `/run/tidewise-helper`, under root-owned `/run`, 0700 and checked on open. The test-only `open` accepts any path, which is by design.
- **`WorkDir` construction (C).**
  - `WorkDir` derives only `Debug`: no `Clone`, `Default` or `Deserialize`, and `path` is private.
  - The only `WorkDir { }` literal is in `open_verified`, which is private to the `workdir` module.
  - `open` exists under `#[cfg(test)]` only, so integration tests, doctests and the binary cannot call it.
  - `unsafe` is forbidden in `lib.rs` and `main.rs`.
  - Production calls `open_default` only (`main.rs`).
- **Refactor behaviour (E).**
  - `runner.rs` `Cleanup` now borrows `&WorkDir`. Its paths are `dir.path().join(name)`, so `remove_work_file` accepts them. A failed removal is still ignored (`let _ =`).
  - `remove_leftovers` now double-checks the file type and keeps the same count semantics.
  - The half-pair removal is unchanged in effect.
  - `file_changes.rs` expected-list edits match the moved lines.
- **Policy (B).**
  - `allow_any=no`, `allow_inactive=no`, `allow_active=auth_admin`, no `_keep`, no `allow_gui`, no `exec.argv1`, no `imply` / `owner` in the file.
  - No `.rules` files are shipped, so admin identities come from the system (wheel on Arch).
  - Remote, SSH and inactive sessions are refused by `no`.
  - `$(command_line)` expansion is single pass.
  - `exec.path` is an absolute path and matches `realpath` exactly.
  - The 80-character cut applies only to `cmdline_short`, not `command_line`.
- **Helper after a hostile argv (A).**
  - `summary_arg` requires exactly `[program, summary]` and keeps raw bytes.
  - `decide` validates stdin first and compares the bytes to the recomputed summary.
  - The log gets the recomputed summary, never the argv text.
  - A mismatch changes nothing. Tests exist for newline, NUL, non-UTF-8 and option-like arguments.
- `cargo test --all` and `cargo clippy --all-targets -- -D warnings` pass.

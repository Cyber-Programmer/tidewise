## Findings

### R-01 (Medium, CONFIRMED) The libraries loaded at run time were found with a regex that misses names, and Q29 says the opposite of the truth
Claim (`docs/security/threat-model.md` question 29, `PKGBUILD:42-51`, `packaging.rs` `the_depends_are_the_list_derived_from_the_built_package`): the run-time libraries are libxkbcommon, wayland, libx11, libxcb, libxi, libxkbcommon-x11, and "no GL/EGL name was found".

Evidence: the analysis script (scratchpad `analyse.sh`) used `strings -a | grep -oE '\blib[A-Za-z0-9_+-]+\.so(\.[0-9]+)*'`. In a Rust binary the strings are packed without separators (`...codelibEGL.so.1`), so `\b` fails and the name is skipped. Running the same search without `\b` on the host-built `target/release/tidewise` (same source and `Cargo.lock`, not the packaged file) gives, besides the six names in `depends`:
- `libEGL.so.1`, `libGL.so.1` (femtovg is an OpenGL renderer: `crates/app/Cargo.toml:14` has `renderer-femtovg`)
- `libXcursor.so.1`, `libXrender.so.1`, `libX11-xcb.so.1` (winit's X11 backend; `libX11-xcb` belongs to `libx11`)
`analysis.txt` lists none of them, and `libX11.so.6` only shows up because it happened to follow a separator.

Failure scenario: on a machine without `libglvnd`, `libxcursor` or `libxrender` (a minimal X11 or Wayland-only install, which `pacman -U`/AUR `makepkg -s` will not fix because they are not in `depends`) the window either opens without GL (software fallback) or does not open at all under X11, depending on how winit handles a missing `libXcursor`/`libXrender`. I did not run the app, so which of the two is not established. Either way Q29 and the comment above `depends` state something false, and the "derived, not guessed" claim is weaker than written. The human's "depends, not optdepends" decision (16 Nov 2026) was taken on this evidence.

Fix:
1. Re-derive from the packaged binary with `grep -aoE 'lib[A-Za-z0-9_+-]+\.so(\.[0-9]+)*'` (no `\b`) and decide on `libglvnd` (owner of `libGL.so.1`, `libEGL.so.1` on Arch), `libxcursor`, `libxrender` (check each owner with `pacman -Qo` in the image).
2. Make it a test instead of a one-time analysis: in the package container test, extract those names from both ELF files, and for each one assert `/usr/lib/<name>` exists after installing the package with only its declared `depends` (the image installs exactly those). A missing file is a missing dependency. The 5.5 text in Q29 then says what is actually proven.
3. Correct Q29 and the `PKGBUILD` comment.

### R-02 (Medium, CONFIRMED gap) No test looks at what pacman runs as root when the package is installed
`tests/container/tests/package.rs`, `packaging.rs`. The package is installed as root with `pacman -U`. An `install=` scriptlet (`.INSTALL` in the archive) runs as root, outside the helper's allow-list (golden rule 2). `.PKGINFO` can also carry `backup`, `provides`, `conflicts`, `replaces`, `install` keys.
- `packaging.rs` never reads `install=`, `provides`, `conflicts`, `replaces`, `backup` (R-03 explains why).
- The container test lists files with `pacman -Ql`, which does not show `.INSTALL`, `.CHANGELOG`, `.MTREE`, `.PKGINFO`. `package_namcap_prints_only_the_accepted_lines` does not forbid a scriptlet (namcap only warns on some contents). The package would be installed by the test, the scriptlet would run, and the test would still pass if it left no file.
- `package_srcinfo_is_what_makepkg_prints` only requires the committed `.SRCINFO` to match whatever the PKGBUILD says.
Failure scenario: a careless or malicious change adds `install=tidewise.install` (and the file) or `provides=('pacman')`/`replaces=(...)`; every test stays green.
Fix (small): in the container test, `bsdtar -tf <pkg>` must list exactly `.BUILDINFO`, `.MTREE`, `.PKGINFO` plus the five files and their folders (no `.INSTALL`, no `.CHANGELOG`); and `.PKGINFO` keys must be in an allow-list (`pkgname`, `pkgbase`, `xdata`, `pkgver`, `pkgdesc`, `url`, `builddate`, `packager`, `size`, `arch`, `license`, `depend`, `makedepend`, `checkdepend`, `optdepend`). Alternatively compare the whole `printsrcinfo` text with one literal expected string.

### R-03 (Low, CONFIRMED) The recipe parser sees only the first assignment and three functions
`crates/helper/tests/packaging.rs:60-104` (`scalar`, `array`, `function_body`). What it does not see:
- `source+=(...)`, `sha256sums+=(...)`, `depends+=(...)`, `options+=(...)`: `array()` matches only a line starting `name=(`.
- A second `name=` or a second `package() {`: `find_map`/`any` take the first, bash uses the last.
- Architecture-suffixed arrays `source_x86_64=(...)`, `sha256sums_x86_64=(...)`, `b2sums`, `sha512sums`: never read. `source_x86_64=('https://…')` with `sha256sums_x86_64=('SKIP')` passes `skip_problem` and every other test (`array(... "sha256sums")` is the only sum read).
- Functions other than `build`, `check`, `package`: `prepare()`, `pkgver()`, `package_tidewise()` (I did not verify makepkg's precedence when both exist, but the test reads neither). The forbidden-word test (`the_functions_run_no_command_that_changes_modes_owners_or_the_system`) covers only those three and is a substring blocklist: `mv`, `rm`, `tar`, `sh -c`, `eval`, `python`, `git`, `install` are not on it.
- Top-level code outside functions, `install=`, `provides`, `conflicts`, `replaces`, `backup`, `noextract`.
- `function_body` ends at the first line that is exactly `}`: a stray `}` line (a here-doc, a `case` written at column 0) hides everything after it from every test, while bash would keep reading.
Effect: the header claim "the recipe can do nothing else to a file" is true of `package()` only. The container test is the backstop for files in `/usr` (exact file set and modes), but it runs only locally, not in CI. For network or build-time actions (`prepare()` with `curl`, a `build()` that edits `$pkgdir`) there is no backstop.
Fix: either (a) test against makepkg's own normalized output: parse `.SRCINFO` (it already expands `+=` and arch suffixes) for the guard and the depends, and have the container test assert `printsrcinfo` has exactly the expected keys; plus (b) an allow-list for the PKGBUILD's top-level lines (every non-comment line outside a function must begin with one of the known variable names, each seen once; the only function names are `build`, `check`, `package`, each defined once). Fail on anything else.

### R-04 (Low, CONFIRMED) The release blocker is documented, but the guard has more gaps than question 28 lists
Question 28 names one gap (CI does not run on tags). Others, in `packaging.rs:352-420`:
1. Only `sha256sums` is read (R-03). Switching to `b2sums` makes the test panic loudly (fine); adding `sha512sums_x86_64=('SKIP')` is silent.
2. `skip_problem` accepts any non-`SKIP` string as a checksum (`'x'`, 63 hex digits). makepkg would reject it later, so this is hygiene only.
3. A source with no `://` (a local file, `foo.tar.gz`) and `SKIP` is allowed outside release builds by design. A VCS source written without a scheme is not a makepkg form, so no bypass found.
4. The guard runs against this repository's PKGBUILD. The AUR repository holds its own copy; nothing ties the two. When the human publishes (M4/M10), the check must run on the file that is pushed.
5. `GITHUB_REF_TYPE=tag` or `TIDEWISE_RELEASE=1` is the whole trigger; `.github/workflows/ci.yml` runs only on push to `main` and on pull requests (lines 5-8), so today it can fire only if someone exports the variable. This is Q28's own gap, restated.
6. The release-time check is a unit test, so `check()` in the PKGBUILD runs it too. With `TIDEWISE_RELEASE=1` in a user's environment, `makepkg` would fail on `SKIP`. That is desired, but it should be documented as intended.
Fix: read `source*`/`*sums*` from `.SRCINFO` (R-03), require 64-hex (or 128-hex for b2) when not SKIP, and put "run `cargo test -p tidewise-helper --test packaging` with `TIDEWISE_RELEASE=1` on the exact PKGBUILD that goes to the AUR" on the M4 checklist next to the tag-CI item.

### R-05 (Low, PLAUSIBLE) `package()` installs the files left in `target/release/` after `check()` has rebuilt them
`PKGBUILD:61-70`. makepkg runs `build()` (`cargo build --release --locked -p tidewise-app -p tidewise-helper`), then `check()` (`cargo test --release --locked`, whole workspace including `tests/container`, `crates/helper` integration tests), then `package()`, which installs `target/release/tidewise` and `target/release/tidewise-helper`. A workspace-wide `cargo test` can recompile dependencies with a different (unified) feature set and relink those two files, so the installed binaries are not necessarily the ones `build()` made. I did not observe a difference; I only note that nothing proves the bytes are the ones from `build()`. What does hold: the package test `package_real_pkexec_runs_the_installed_helper_end_to_end` runs the *installed* helper, so a broken one would show up. A different feature set in the helper could still change behaviour that no container test covers.
Fix (cheap): `CARGO_TARGET_DIR="$srcdir/target-check" cargo test ...` in `check()`, or run `check()` before `package()` with a separate target dir, so `package()` installs exactly what `build()` produced. Both are Arch-guideline compatible.

### R-06 (Low, hardening) Build-stage trust and "tested tree" mismatches in the container harness
1. `Containerfile.package:30-33`: a builder-user shell sources `./PKGBUILD` and its stdout (not only the arrays; any `echo` at the top of the recipe) is written to `/tmp/recipe-deps`, which root then feeds to `pacman -S --noconfirm --needed -`. `pacman -S` accepts URL targets, so a hostile `depends=('https://…pkg.tar.zst')` would be fetched and installed as root inside the build stage. The same pattern in stage 2 reads names from `.PKGINFO` with `sed`. Impact is limited to a throwaway build container and a recipe that the human reviews, and `packaging.rs` pins `depends` exactly (R-03 notes `+=` is not seen). Still cheap to close: filter the list with `grep -E '^[a-z0-9@._+-]+$'` before `pacman -S -`, and fail if a line is dropped.
2. `run.sh:55-58` warns, and does not stop, when the working tree is dirty. `packaging.rs` reads the working tree; the container builds HEAD. A green `cargo test --all` plus a green container run can therefore describe two different recipes. Fail (or build from the working tree with `git stash create`) when `git status --porcelain` is non-empty for `packaging/` or `Cargo.lock`. Right now the working tree has an uncommitted `docs/security/threat-model.md`, which is harmless, but it shows the warning path is live.
3. `cargo build --locked` runs at `build()` time with network (Containerfile comment says so). `Cargo.lock` has 537 registry entries, 0 git sources, and `deny.toml` has `unknown-registry`/`unknown-git = deny`, so crates are checksum-pinned. The Arch Rust guideline fetches in `prepare()` (`cargo fetch --locked`) so that `build()` can be offline; not done here. Info only.

### R-07 (Info) Claims that go further than the tests
- `package_real_pkexec_runs_the_installed_helper_end_to_end` and its siblings run `pkexec` as root, which is authorized whatever the action (same caveat as review 5.4b R-04). They prove the installed helper starts under the real `pkexec` with the right `argv[0]` and the summary check passes; they do not prove pkexec selected `io.github.tidewise.helper`. `package_polkitd_lists_our_action_from_the_policy_the_package_installed` proves polkitd loaded the action with the right `exec.path` text, which is the most that can be done without a non-root session. The header of `package.rs` does not repeat the caveat. Add one sentence.
- Threat model T-03 says directories are `0755`. `assert_root_owned_and_closed` asserts root:root and no special/group-write/other-write bits (mask `0o7022`), so a 0700 folder would pass. Restrictive modes are not a security problem, but the text and the test differ. Say "not writable by group or others".
- `HELPER_ARGV0` in `tests/container/tests/common/mod.rs:23` is a literal, not `HELPER_PATH`. The chain still closes: `packaging.rs` ties the PKGBUILD destination to `HELPER_PATH`, `polkit_policy.rs` ties the policy to it, and the container tests compare the installed file and the policy to the literal. Fine, but Q23's "asserts that the installed file's real path equals `HELPER_PATH`" is true only through that chain.
- `ACCEPTED_NAMCAP` matches as substrings of a line, so the loader line accepts any file name after "by file". Acceptable: it is the same message for each ELF file.
- `docs/ENGINEERING.md` and `README.md` are unchanged in this branch (the brief asked me to check them): nothing to verify there. `CLAUDE.md` gained the ArchWiki note; `docs/PLAN.md` gained one "Ideas for later" paragraph.
- CLAUDE.md asks that `crates/helper*` is touched only after asking. The branch adds `crates/helper/tests/packaging.rs` (test only). I did not see the approval in the repository; the author should confirm it was given in the session.
- The package cannot be built from the AUR as it stands (`source=("tidewise-0.1.0.tar.gz")`, a local file). That is the documented SKIP blocker, not a new finding.

## Checked and found sound

- **Who can write what.** All five files install as `root:root` because `package()` runs under makepkg's fakeroot; the container test confirms owner and mode on the installed files and on every ancestor up to `/` (`package_files_are_root_owned_with_the_exact_modes_and_nothing_is_writable_or_setuid`, `package.rs:~320-355`), uses `symlink_metadata` (no following), and asserts the exact file set from `pacman -Ql`, so an extra file, a hard link, a symlink or a setuid file under `/usr` would fail. Modes are explicit (`-Dm755`/`-Dm644`), so a user's umask cannot make anything more permissive: `install -D` creates parent directories at 0755 minus umask, which can only tighten them.
- **Helper mode.** `install -Dm755` on the helper, never `-m4755`; `packaging.rs` checks the mode has three digits and no group/other write bit (a four-digit setuid mode fails), the container test checks `mode & 0o7022 == 0` and exactly 0755.
- **HELPER_PATH, policy `exec.path`, install path.** The PKGBUILD destination is compared to `HELPER_PATH` (`packaging.rs` `expected_installs`), the policy annotation to `HELPER_PATH` (`the_packaged_policy_names_the_helpers_installed_path`; `polkit_policy.rs` from 5.4), and the container test asserts the installed policy (as read by polkitd) and the installed file at the same path with no symlink in it (`canonicalize` equals the path). I mentally mutated each of the three: each is caught by a different test.
- **`package()` is only `install` lines.** `installs()` requires exactly four words and `install -Dm…`, compares source, destination and mode with an exact list. `"$pkgdir"` is quoted and starts `"$pkgdir/usr/`. A command substitution without spaces inside the destination (`"$pkgdir/usr/$(id)"`) would pass the shape test but fails the exact-list comparison.
- **No RPATH/RUNPATH.** The recipe has no `rustflags`/`rpath` text in code lines, there is no `.cargo/config.toml` and no `[build]`/`[profile]` link flags, and the one `build.rs` (`crates/app/build.rs`) only calls `slint_build::compile`. The container test runs `readelf -d` on every ELF file the package owns, non-vacuously (both binaries must be in the list).
- **Network and unverified code.** `cargo build/test --locked`; `Cargo.lock` has no git sources; `deny.toml` denies unknown registries and git. `source` is one local tarball; no `curl`, `wget`. `pkgver` is tied to the workspace version.
- **`--disable-download-timeout`** appears in four `pacman` calls, all in `RUN` lines of `Containerfile.package` (image build time), and nowhere else in the repository (`run.sh`, tests, helper, docs aside). `-Syu` is used with `-S` only after a full upgrade (rule 4), and the second stage installs against the base image's database, which is the same Archive day and was refreshed once at its own build.
- **Container harness rules.** `run.sh` still refuses root, requires rootless podman, runs `podman run` with `--network=none`, `--security-opt=no-new-privileges`, no `--privileged`, and mounts only the test binary and `tidewise-helper`, both `:ro`. The package tarball is copied into the image build, not mounted. The package test file runs in its own fresh container and uses `Installed` with a `Drop` that removes the package. The build base image is pinned by digest and the Archive day equals `Containerfile`'s (`2026/11/08`).
- **Removal and the work folder.** `/run/tidewise-helper` is not owned by the package (no `tmpfiles.d`, nothing under `/run` in `-Ql`), is created by the root helper, stays root, 0700, empty after a job, and lives on tmpfs under a root-owned `/run`, so a user cannot pre-create it. `package_removal_leaves_nothing…` asserts every package file is gone and `/usr/lib/tidewise`, `/usr/share/licenses/tidewise` no longer exist.
- **Golden rules.** 1 (the app is never root: `Exec=tidewise`, no `pkexec` or `sudo` in the desktop entry, asserted), 2 (no change to `crates/helper-protocol`, `crates/helper/src`, the allow-list), 3 (no shell in the recipe functions), 8 and 9 (nothing in the diff touches protected packages or `db.lck`). The test harness runs programs by absolute path with a cleared environment (`run()` in `package.rs`, `pkexec()` in `common/mod.rs`).
- **depends, for what the dynamic linker shows.** `readelf NEEDED`/`ldd` agree with `glibc`, `libgcc`, `fontconfig`; `libgcc` rather than `gcc-libs` is right (namcap: "implicitly satisfied"). `pacman` and `polkit` are programs, the helper runs `/usr/bin/pacman` and `pacman-conf` (part of `pacman`), the policy needs polkit. The three namcap warnings accepted for them are justified. The only part that is not sound is the run-time list (R-01).
- **.SRCINFO** is byte-compared with `makepkg --printsrcinfo` in the container and checked key by key in the unit test.

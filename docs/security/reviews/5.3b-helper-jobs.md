# Independent review: 5.3b helper jobs (branch `feat/helper-jobs` against `main`)

## Scope and method

Read: `docs/security/threat-model.md` (whole, rows T-01 to T-23, sections 5 and 6), decisions 0005 and 0006,
`CLAUDE.md` golden rules, the 5.3a review, and every non-test line of `crates/helper/src/`
(`pacman_args.rs`, `env.rs`, `output.rs`, `progress.rs`, `workdir.rs`, `runner.rs`, `flows.rs`, `run.rs`, `gate.rs`,
`journal.rs`, `main.rs`, `testing.rs`), `crates/helper/tests/file_changes.rs`, the `crates/helper-protocol` diff
(`event.rs`, `validate.rs`, `lib.rs`), `crates/names`, the relevant parts of `crates/pacman` (`parse_qu`,
`install_decision`), `tests/container/run.sh`, `tests/container/tests/helper_jobs.rs` (the caller-goes-away, hangup and
no-journal tests), `common/mod.rs::reset_world`, and the saved fixtures in `tests/fixtures/helper-jobs/`. The
container tests were read, never run.

Ran: `cargo test --offline -p tidewise-helper -p tidewise-helper-protocol` (207 + 2 + 8 + protocol tests, all pass);
the debug helper as an ordinary user with `{}` on stdin (refuses: "must be started as root", exit 2); a script that
checks that every snake_case name in backticks in `threat-model.md` and `0006-*.md` exists as a `fn` (result in R-07);
a grep of the non-test helper code for `as` casts, `+`/`-` arithmetic, slicing, `unwrap`, `expect`, `panic`; a look at
`rustix-1.1.6/src/process/umask.rs` in the local cargo registry. Not run (as instructed): podman, `run.sh`, fuzzing,
pkexec, any pacman write. I did not run `cargo clippy` (a build was running); the crate's `deny(...)` lints plus my
grep are the basis for the "no panic path" statements.

**Result: no High and no Medium finding.** I could not make a request value reach pacman's argv outside `--`, could
not fool the dry-run comparison with anything an attacker controls, and found no path in the helper's own code that
panics, removes `db.lck`, or follows a planted path. What is left is Low and Info: a missing tripwire for the one
invariant that rests on a pacman flag (no removals), a state change (`-D --asdeps`) that is wider than its purpose, a
`-Qu` error that is read as "nothing pending", a few places where the helper can stall or lose information, and
documentation that no longer matches the code (five cited test names do not exist).

## Findings

### R-01  Low  CONFIRMED: nothing detects a removal, although "no removals" now rests on one pacman flag

`crates/helper/src/flows.rs:207-230` (`post_check`), `output.rs:94-108` (`count_not_installed`),
`progress.rs:103-117` (`is_package_line` already recognises `removing <name>...`).

Rule 10 allows `--noconfirm` only when there are "no removals". The dry run cannot show that: decision 0006 measured
that `--print` omits the removal a replacement causes. The helper therefore relies on `--ask 66` (flag 2) plus pacman's
"conflict defaults to no". Flag 2 is tested with real pacman; but if any other path removes a package (another
question type, a future pacman default, a hook, a version where the inversion differs), the job ends `Ok` with no
signal: `post_check` only counts *listed* packages that are missing, and a removed package is not on the list. The
journal says `ok`, priority 6.

Failure scenario: an update whose real run prints `removing foo...` for a package that is not in the confirmed list.
Result: `{"finished":"ok"}`, exit 0, nothing in the notice or the journal.

Fix (cheap, no new pacman call): in `real_run_and_after`, count lines the real run printed that match
`removing <word>...` (the tracker already parses that shape) and, if the count is above zero, emit a new fixed
`Notice` (count only) and log it; or fail the job's final line with a fixed text. This also turns a wrong reading of
flag 64 or 2 into something visible. Note that a scriptlet can print such a line, so treat it as a tripwire, not proof.

### R-02  Low  CONFIRMED: `-D --asdeps` is run on every chosen provider, including one the user already had installed explicitly

`crates/helper/src/flows.rs:190-196`, `pacman_args.rs:71-76`, `crates/helper-protocol/src/validate.rs:140-144`.

`validate` requires a chosen provider to be in the confirmed list, nothing more. `pacman -S extra/<provider>` on an
already installed package is a reinstall (it prints and installs), so it passes the dry-run comparison. After the real
run the helper marks it as a dependency unconditionally.

Failure scenario: request `install` with `targets=[extra/foo]`, `providers=[{dependency:"x", chosen:extra/firefox}]`,
and a confirmed list `[extra/foo, extra/firefox]` (what the dry run prints). `firefox`, which the user installed
by hand, becomes "installed as a dependency". A later "remove unneeded packages" (M5) would offer or remove it. The
user approved a prompt that names both packages, so this needs their approval, but the install reason is changed
without the dialog saying so, and the legitimate flow (the provider question only arises when no provider is
installed) never needs it.

Fix: before the real run, ask `pacman -Qq -- <providers>` (read, no lock) and run `-D --asdeps` only for providers that
were not installed before. Or refuse a request whose chosen provider is already installed.

### R-03  Low  CONFIRMED: `pacman -Qu` exit status 1 is accepted whatever it printed on stderr

`crates/helper/src/flows.rs:133`.

`!matches!(output.exit, Some(0) | Some(1))` treats exit 1 as "nothing pending" even when stderr holds an error
("error: ..."), because `-Qu` exits 1 both for "no updates" and for most failures. The fixtures have only exit 0 for
`qu-pending`; there is no saved real failure and no unit test with exit 1 plus stderr (the nearest test,
`an_unreadable_update_list_is_a_failure_and_nothing_else_runs`, uses exit 2).

Failure scenario: sync database unreadable or half-written, `-Qu` prints `error: ...` and exits 1, stdout empty. The
install check passes ("no pending updates"). The dry run that follows normally fails too, so the practical exposure is
small; but rule 4 protection should not depend on the next command failing.

Fix: accept exit 1 only if stdout and stderr are both empty (or stderr has no line starting with `error:`).
Add a unit test with `out(1, "", "error: ...")` and a container fixture of a real failing `-Qu`.

### R-04  Low  PLAUSIBLE: an explicitly requested target can be a downgrade, and nothing in the dry run or the summary says so

`crates/helper/src/pacman_args.rs:51` (`--print-format "%r/%n %v"` prints only the repository version),
`flows.rs:145-171`.

The comparison sees the repository version, not what is installed. For a target whose installed version is newer than
the repository's (a testing build, a local build, a repository rolled back), `pacman -S repo/name` replaces it with the
older repository version, and so does the real run. The post-check then calls it correct ("installed at the confirmed
version"). I did not run it (it needs a write); this is how I understand `-S <target>` to behave with a newer local
version, so I mark it PLAUSIBLE. `-Su` never downgrades.

Fix: before the real install, `pacman -Q -- <targets>` and refuse (a fixed error) if the installed version is newer
by `vercmp`; or add `%o`-style old-version data to the confirm screen (the app, not the helper). At least say so in
the threat model.

### R-05  Low  CONFIRMED: the helper blocks on a stalled reader of its stdout while pacman runs on, and its later steps wait

`crates/helper/src/run.rs:181-185` (the event callback calls `write_line`, a blocking `write_all` + `flush`),
`runner.rs:202-215` (the event is written from inside the wait loop).

The "reader went away" case is fine (EPIPE, SIGPIPE is ignored by Rust's runtime, the error is dropped; the
container test covers it). The *stalled* reader is not: if the caller keeps the pipe open and stops reading, a
transaction that emits more than the pipe buffer (64 KiB) of progress lines (a thousand packages at roughly 60 bytes
a line) blocks the helper inside the callback. pacman is in its own group and finishes; the helper does not collect
it, does not run `-D --asdeps`, the post-check, or the final journal entry, and stays alive as root until the reader
reads or closes. Same class as the stdin residual in T-07, on the output side. Not a privilege issue (the caller
already controls whether it reads), but the audit trail ("finished") is exactly what a hostile caller can withhold.

Fix: never block the runner loop on caller I/O: send events through a bounded queue to a writer thread and drop
progress events when it is full (the final lines can wait). Or document it as accepted in T-17.

### R-06  Low  CONFIRMED: a half-success is logged as `ok`; notices and failure details are not in the journal

`crates/helper/src/run.rs:187-192`, `journal.rs:62-95`.

`Stage::Finished` carries only the outcome code. A run that ends `ok` after a declined replacement, or a
`PackagesNotInstalled(n)` notice, is logged exactly like a clean run (priority 6, `TIDEWISE_OUTCOME=ok`). The only
record of "n packages not installed" is the stdout line the caller may have discarded. `pacman.log` still records the
package changes, so this is a forensics gap, not an integrity one.

Fix: add a fixed `TIDEWISE_NOTICES=<count>` or put the notice count in the finished entry, priority 4 when it is above
zero.

### R-08  Info  CONFIRMED: a helper that dies with a reused pid can fail its own first job

`crates/helper/src/workdir.rs:99-116` (`remove_leftovers`), `119-130` (`create_output_files`, `create_new`).

Leftover removal skips files whose pid is alive; the new helper's own pid is alive by definition. If a killed helper's
pid is reused by the next helper (pid space wraps), `tidewise-helper-<pid>-0.out` already exists, `create_new` fails
with EEXIST, the job ends with the fixed "work folder could not be used" text, and the file stays until a helper with
another pid runs. Availability only, fails before pacman runs, probability about 1 in `pid_max` per leftover. Fix:
skip the *own* pid in the "is alive" test (`pid != std::process::id()` counts as dead), or use a random suffix.

### R-09  Info  CONFIRMED: the work files are unbounded on disk; stderr keeps the head, not the tail

`runner.rs:219` and `269-278`, `runner.rs:31-33`.

The 4 MiB and 64 KiB caps limit memory only. pacman (or a scriptlet it runs) can write any amount to the tmpfs files
(`/run`, RAM); T-22 states this honestly for hostile packages. Separately, `read_capped` takes the first 64 KiB of
stderr and `Details` the first 4 KiB of that: if pacman prints many `warning:` lines before the `error:` that stopped
it, the error is cut off and the user sees only warnings. Fix: keep the last N bytes of stderr (seek to the end minus
the cap), and say in T-22 that the cap is for memory.

### R-10  Info  CONFIRMED: a few runner edge cases that the code handles differently from the comments

`crates/helper/src/runner.rs`.

- Line 207: `try_wait` returning `Err` returns `RunnerError::Io` while pacman may still run; the `Cleanup` guard then
  removes the files under it and nobody waits for it. `try_wait` fails in practice only on ECHILD, so this is unlikely,
  but the comment "this loop never gives up on it" is not true for this arm.
- Line 210: the timeout kills the child with `child.kill()` (SIGKILL to the pid, not the group). It is only used for
  commands that take no lock and spawn nothing in the measured cases, so it is fine today; if pacman's `XferCommand`
  or a future read command forks, the grandchild survives. `kill(-pgid)` would need `unsafe` or `rustix`
  (already a dependency, `process` feature has `kill_process_group`).
- `process_group(0)` keeps pacman in the helper's session. With a controlling terminal (helper started from a shell)
  a scriptlet that opens `/dev/tty` would get SIGTTIN, stop, and hold the lock with no timeout. No tty exists when the
  app starts the helper; the risk is for hand starts only.
- `-Sy` has no timeout and holds the lock (T-17 argues this on purpose; pacman's own download low-speed timeout is the
  only limit).

### R-11  Info  CONFIRMED: `pacman_args::args` re-checks the allow-list but not the length

`crates/helper/src/pacman_args.rs:119-128`.

`checked` uses `is_helper_repo_name` (64-byte cap) and `is_valid_package_name` (no length cap; the 128-byte cap is
`is_package_name` in `validate.rs`). Unreachable from the request path, because `validate` runs first and caps the
count and length. It matters only as defence in depth, which the module's own header claims ("checked once more
against the same allow-lists"). Fix: export one `is_valid_package_ref` from the protocol crate and use it in both.

### R-12  Info  CONFIRMED: the "only the listed places touch files" guard is a prompt for review, as it says, with gaps

`crates/helper/tests/file_changes.rs:13-28` and `41`.

It is line-based and word-based: `unlink`, `rustix::fs::{unlinkat,openat,renameat}`, `hard_link`, `File::options()`,
`set_len`, a call split over two lines, or a path built from two string pieces would not be found. The split on the
first `#[cfg(test)]` also drops everything after it in a file (today only `lib.rs` has it early and holds no code
after). The file's own header says "not a proof of absence", and the mutation check in the commit message (adding a
removal fails both tests) is plausible for the listed words. No fix needed beyond keeping the wording modest in the
threat model (T-10 and T-22 call it a "source guard").

### R-13  Info  CONFIRMED (known): an update that stops after `-Sy` leaves the lists newer than the packages

`flows.rs:93-106`; open question 12 and decision 0006 both state it.

Three code paths end an update after the sync and before the upgrade: `TransactionChanged` from the dry run, a helper
killed (Q16), and a stalled caller (R-05). The cost is the one rule 4 names: a later plain `-S` by the user (outside
Tidewise) is a partial upgrade. Tidewise's own plain install refuses while updates are pending (`check_nothing_pending`),
so it does not make it worse. Nothing new to fix; only note that the "update" confirm list is computed before the sync,
so `TransactionChanged` after `-Sy` happens whenever a mirror moved in between, not only under attack.

## Checked and found sound

- **Argv construction** (`pacman_args.rs`). One template per command; everything before `--` is a fixed string;
  names only after `--`; a name or repo with `-`, `.` prefix, `/`, space, NUL, `=`, `<`, `>`, `:`, `*`, non-ASCII or
  over 64 bytes (repo) is refused as a whole. `repo/name` is safe: the repo allow-list excludes `/`, `local`, and
  anything but `[A-Za-z0-9@._+-]` not starting with `-` or `.`, and the name allow-list has no `/`, `:` or `=`, so
  pacman cannot read a path, file target, URL or versioned dependency. `-D` and `-Q` take only bare names.
  `--noconfirm --ask 66` appear exactly on `RealInstall` and `RealUpdate`; `-y` only in `Sync`. There is no
  `-U`, `-R`, `-dd`, `--overwrite` or `--needed` in any command (the exhaustive `all_commands()` tests plus the
  type: `PacmanCommand` has no free-form variant).
- **No removal or downgrade request exists in the helper.** The only `-D` is `--asdeps`. A removal can come only from
  pacman's own questions (see R-01), and the conflict default is "no".
- **Dry-run comparison** (`output.rs:55-71`). Sorted multiset of (repo, name, version) with exact string equality:
  a duplicate line, an extra or missing line, a different version, epoch, or repository, or a different order of the
  same lines all behave correctly (the first four differ, the last is accepted on purpose). Output that is not
  exactly `repo/name version` per line, has `\r`, a blank line, a trailing space, a warning or a prompt is refused,
  and the parse is capped at 5 000 lines. Truncated output (4 MiB) and timeouts are refused before the parse. Neither
  the dry run nor `-Qu` can be forged by a package's scriptlet: they run no scriptlets and only the real run's output
  is package-influenced.
- **Check order in the flows** (`flows.rs`). Lock look, then `-Qu` (install) or `-Sy` once (update), then the dry run,
  then the real run. `-Sy` is not reachable from the install flow (`a_plain_install_never_syncs...`), never twice,
  never before a plain `-S`. A dry-run mismatch never reaches the real run. `Names::Optional` applies only to the two
  update commands.
- **Lock handling.** `db.lck` is only passed to `fs::symlink_metadata`; any error but `NotFound` counts as present; no
  creation, removal or open. The three lock texts are matched at line start, so a scriptlet that merely mentions them
  mid-line does not count; a scriptlet that prints one at line start can only turn a real failure into the fixed
  `DatabaseLocked` text, which is harmless. pacman's own advice to remove the lock is never copied: any lock failure
  becomes `ErrorKind::DatabaseLocked` with a fixed text (fixtures `lock-install.err`, `lock-asdeps.err` contain the
  advice and the test asserts it is dropped).
- **Work folder** (`workdir.rs`). Created 0700 (the umask is already 022 and the explicit mode is 0700), verified with
  `symlink_metadata` (symlink, file, dangling link refused), owner uid 0, mode exactly 0700; never repaired.
  Files with `O_CREAT|O_EXCL|0600`, names from our own pid and a counter, no caller-chosen part. Leftover removal
  matches only `tidewise-helper-<digits<=10>-<digits<=10>.(out|err)`, regular files by `DirEntry::file_type` (no
  symlink follow), and only when `/proc/<pid>` is missing; an extra-wide pid, a look-alike, a directory, a symlink are
  left alone. pid reuse errs toward keeping a file. A different helper's live files are skipped. `/proc` is required
  for the start checks anyway, so "no /proc" cannot make everything look dead. A hostile local user cannot touch
  the folder (`/run` and the folder are root-only), so the check-then-use window is not reachable by them.
- **Inherited descriptors.** The child gets `stdin` null and both output files as 1 and 2; all other helper
  descriptors are close-on-exec in Rust; the start check already refuses any inherited descriptor above 2.
- **Environment and umask.** `env_clear()` then exactly `PATH=/usr/bin`, `LC_ALL=C`; absolute program path;
  `set_umask_022()` is the first statement of `main`, before `/proc` is read, before the folder or any file is
  created; `rustix::process::umask` is a safe function gated by `fs` (verified in the local registry copy), so
  `forbid(unsafe_code)` holds.
- **Panics and overflow.** A grep of the non-test code found no `unwrap`/`expect`/`panic`/indexing/`as` casts;
  counters are `saturating_sub`, `wrapping_add`, guarded `+= 1` (`current < total`, `total <= 5 000`), or `u32::try_from`
  with a saturating fallback. Memory is bounded: stdin 2 MiB (+1), stdout capture 4 MiB, one partial line 64 KiB,
  5 000 parsed lines. `Details` worst case with JSON escaping (4 096 `\n` or `"`) is 8 192 bytes, under the 16 KiB
  event-line cap (tested).
- **try_wait loop.** No busy loop (20 ms sleep), a final drain after exit, a partial last line is kept and delivered,
  a real transaction is never killed, no zombie in the normal path.
- **Signals.** SIGPIPE: Rust ignores it for the helper (no `unix_sigpipe` attribute anywhere) and resets it to default
  in the child; the helper survives a closed stdout (tested in the container, as exit 0). pacman writes to files, so
  a vanished reader cannot kill it. A SIGHUP to the helper's group does not reach pacman (own group). The
  documented residual (the helper itself dies, `-D --asdeps` and the second half of an update do not run) is stated
  honestly in decision 0006, T-17 (residual paragraph) and Q16, and the container test asserts the provider stays
  "explicit".
- **Error text.** Every failure is a fixed sentence, `DatabaseLocked`, or pacman's stderr passed through `Details`
  (control characters and direction marks removed, 4 KiB). No path, argv, environment or request text is echoed;
  the journal gets the recomputed summary only, ASCII-cleaned, with no field or line injection.
- **Notice.** `PackagesNotInstalled(n)` is a count computed from `pacman -Q` output; a package's output cannot reach
  it. It cannot be forged by the app side either: the parser is strict (`bad_notice_lines_are_refused`).
- **`NotImplemented`.** No reference remains in `crates`, `tests`, `fuzz` or `docs` except the deliberate "no longer
  known" test and the (stale) citations in R-07.
- **Rule 1, 3, 6, 9.** The app side is untouched. No shell, no `sh -c`, no relative program path. One helper run is one
  transaction (R-05 and the update flow notwithstanding). `db.lck` is never created, changed or removed.
- **Carry-over R-01 of the 5.3a review (userns "root").** With jobs, a user-namespace "root" (`unshare -r`) passes the
  uid check, but `main`'s work-folder check wants a folder owned by uid 0; a real root-owned `/run/tidewise-helper`
  shows as an unmapped owner inside the namespace, and `/run` is not writable there, so `make_runner` fails closed
  before any pacman command. Marked as reasoning, not as a run: I did not execute a valid request, because that would
  write journal entries to the host journal. Worth a container test (`unshare -r` plus a valid request, expect the
  work-folder error) if the human wants this proven.
- **Container tests, read-only review.** `--test-threads=1` and a fresh container per file, `reset_world` restores the
  repository, removes dummy packages, `/tmp/tidewise-*` markers and the work folder, so state does not leak between
  tests. The one timing-based wait (`wait_for_file(a) || wait_for_file(b)`) is a start marker with 30 s and 1 s limits,
  not an assertion of timing. The mutation checks in the commit message (`--ask 0`, no umask call, no
  `process_group(0)`) are plausible against what the tests assert.

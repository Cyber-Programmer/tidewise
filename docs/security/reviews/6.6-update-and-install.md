## U-01: the proposed rule, measured (28 Nov 2026)

Proposal: "what the chosen package brings" = the private `-Su` of targets + chosen, minus the private `-Su` of
targets; refuse if adding the chosen package changes what was listed. Measured with pacman 7.1.0 in the test image
(`--network=none`, dummy repository). Lines are package names.

| Case | `-Su` alone | `-Su targets` | `-Su targets chosen` | Proposal |
|---|---|---|---|---|
| M1, the U-01 reproduction: chosen `pa` needs `pa-core` (also provides the name) and a bumped `libx` | libx bar | pa-core libx pa app bar | the same | **refuses**: the difference is empty, because `pa` is pacman's own default |
| M2, chosen `zc` is not the default (`aa`), needs `zc-core` (also provides the name) | up | aa app up | zc-core zc app up | **refuses**: `aa` disappears ("changes what the update resolves to") |
| M3, only the update pulls `oth` (by name), which also provides the name; chosen `pb` | oth upg | oth app upg | pb oth app upg | refuses `oth`, as wanted |
| M4, `zdk` needs `jre` by name; the update's own need makes `jre` the default | jre upg | jre app upg | jre zdk app upg | **refuses**: `jre` is not in the difference, though pacman asks nothing for it |

With the plain update as the baseline (`-Su chosen` minus `-Su` alone) M1, M2 and M3 come out right and M4 is still
refused. **Neither form was built.** What was built (the human's decision): reachability by exact-name dependencies
(`brought_by_name`), no dry run, `PrivateDryRunInstall` removed. It accepts M1, M2 and M4 and refuses M3; M1, M3 and
M4 are container tests against the real helper.

Also measured (M5): a dependency written as a package's own name takes that package without asking, although another
package provides the name.

Read from this machine's sync lists (15786 packages): 27 pairs where one provider of a name depends **by name** on
another provider of it; 25 without a version rule, 2 with `=` (`qemu-desktop`, `qemu-full`), none with `>=` or `<`.
(The review's `jdk-openjdk` → `jre-openjdk` example is not such a pair today.)

## 1. Verdict in plain words

- **One High (R-01), found by B only.** If whatever starts Tidewise has set "ignore SIGCHLD" (a launcher, a script, an accident),
  the helper cannot see pacman finish, and the update stops right after its one `-Sy`. That is the partial-upgrade state
  rule 4 forbids, and no test starts the helper that way. I measured the helper's half of the claim (section 3).
- **Nothing lets a caller make root run something outside the allow-list.** A, B and C all found the names, parsing, argv
  templates, runner, removal, work folder, journal and polkit policy sound.
- **Eight Mediums, all "proof missing or cannot fail" or "needs one more mistake"**: the known update-syncs-first gap (R-02),
  inherited resource limits (R-03), a caller that freezes or parks the helper (R-04), no automated ordinary-caller pkexec
  proof (R-05), the ASCII-only test (R-06), hand-written command lists (R-07), rule 10's "providers named" unchecked (R-08),
  real-pacman proofs outside CI (R-09).
- **By your definition, R-02, R-03 and R-04 also touch rule 4.** The reviewers rated them Medium because the user must still
  approve a genuine prompt. Section 4 asks you to make that call.

## Review A: the request path (helper-protocol, names, helper gate/flows/runner/pacman_args/output/progress/removal/workdir/journal)

Reviewer A, read-only, no cargo/containers run. Method: pass 1 from CLAUDE.md, decision 0005, threat model and the code only; pass 2 after reading docs/security/reviews/*.
Result in one line: no High found. Three Medium, three Low, a few Info. The allow-list, argv construction, validation and journal are sound; the weak spots are what the *caller* controls around the helper (inherited limits, its stdout, timing), and one accepted rule-4 gap that is more common than the docs suggest.

### Findings

#### A-01 (Medium, pass 1, confidence medium-high): the caller's resource limits are inherited by root pacman
- Where: `crates/helper/src/main.rs:30-40` (start-up sets only umask and cwd), `crates/helper/src/env.rs:17-24`, `crates/helper/src/runner.rs:140-148` (`pacman_command`: `env_clear`, but nothing about limits).
- Fact base: pkexec (setuid) does `setuid` and `execv`; it does not reset rlimits, cgroup, nice or oom_score_adj. Limits survive `execve` and the uid change. `RLIMIT_FSIZE` and `RLIMIT_CPU` apply to root too (`RLIMIT_NPROC` mostly does not). grep of threat model and all reviews for rlimit/ulimit/FSIZE/SIGXFSZ: no hit. T-08 lists env, cwd, umask, fds, signals, not limits.
- Scenario: a process of the user runs `prlimit --fsize=1000000 pkexec /usr/lib/tidewise/tidewise-helper "update system (3 packages)" < valid-request` (or `--cpu=2`, `--as=…`, `--nofile=8`). The user sees a genuine Tidewise prompt (T-02) and authenticates. The helper passes all checks, runs `-Sy`, the dry run, then the real `-Su`. The first file write above 1 MB makes the kernel send SIGXFSZ, whose default action kills pacman in the middle of unpacking: half-written package, stale `db.lck` (rule 9 then forces "wait and explain"), part of the upgrade installed (rule 4). The helper's `process_group(0)` does not help (a limit signal is not a tty signal) and the post-check only counts. A cgroup `MemoryMax` (user can create transient scopes) gives the same through the OOM killer.
- Why Medium and not High: needs the user to approve a prompt for a request that is otherwise valid; effect is integrity/availability of the system, not code execution. By the fixed scale it touches rule 4 with no test failing, so I flag the argument for High; I rate Medium because the authorisation is still explicit.
- Proposed proof (must fail first): container test `limits_given_by_the_caller_do_not_reach_pacman` in `tests/container/tests/helper_jobs.rs`: start the helper with `prlimit --fsize=65536 --cpu=1 --as=…` as wrapper (or `setrlimit` in a pre_exec of the spawn), a fake pacman script that writes `/proc/self/limits` to the work folder; assert "Max file size", "Max cpu time", "Max address space", "Max open files" equal the helper's chosen constants (unlimited / 1048576). Unit side in `env.rs`: `the_limits_are_reset_to_fixed_values_whatever_the_caller_had` reading `/proc/self/limits` after `reset_limits()`. Fix idea: `rustix::process::setrlimit` (safe, rustix already a dependency) at start of `main`; cgroup limits can only be documented. Needs the human's OK (crates/helper).

#### A-02 (Medium, pass 1; disagrees with accepted open question 12): `-Sy` on the real database happens before the confirmed list is compared
- Where: `crates/helper/src/flows.rs:126-164` (`update_job`: Sync, then `dry_run`, mismatch returns `TransactionChanged`).
- Scenario (normal, not hostile): the app's confirm list was made from the user-side, un-synced database (the helper is the only thing that may run `-Sy`). Any mirror change since the last sync makes the helper's list differ. Helper: `-Sy` succeeds (real `/var/lib/pacman/sync` now newer than the installed packages), dry run differs, `TransactionChanged`, exit. State: lists newer than packages. A later plain `pacman -S foo` by the user or any other tool is a partial upgrade (rule 4). Hostile variant: any approved request with a wrong `transaction` list is a "-Sy only" primitive. Same state if the helper is parked (A-03).
- Q12 calls this "wording mitigation, deferred to M4", and says the decision must be settled "before the update flow is built". The helper's update flow is built and tested as is (`a_system_update_syncs_once_compares_then_updates_without_another_sync`); no test pins what happens to the real lists on a mismatch. I disagree that wording is enough for a rule the project calls golden: this is the expected outcome whenever the lists moved, not an edge case.
- Proposed proof (red first): container test `a_changed_update_list_leaves_the_real_sync_databases_untouched` in `helper_jobs.rs`: stale repo, request list differs from the new repo, assert outcome `transaction_changed` AND sha256 of every `/var/lib/pacman/sync/*.db` unchanged (fails today). Unit side: `flows.rs` `a_refused_update_list_never_ran_the_real_sync` (the Fake's `ran` list must not contain `Sync` before the compare; needs the private-copy design of Q12, e.g. `-Sy --dbpath <private copy>` for the dry run).

#### A-03 (Medium for A-03a, Low for A-03b; pass 1; disagrees with accepted Q19a): a hostile caller controls the helper's stdout and stdin, so it can freeze or time-shift an already authorised root process
- Where: `crates/helper/src/run.rs:210-213` (`write_line` blocking inside `on_event`, called from `runner.rs:222-236` drain loop), `crates/helper/src/input.rs:23-33` (`read_to_end` with no timeout), `flows.rs:139-141` (the first event arises inside `-Sy`).
- A-03a: the caller gives the helper a stdout pipe it has pre-filled (or shrunk with `F_SETPIPE_SZ`) and never reads. First progress event (":: Synchronizing package databases...") blocks `write_line` while pacman `-Sy` finishes in its own process group. The helper then waits forever: real lists refreshed, no upgrade, dry run and `-Su` never run (same state as A-02), the authorised root process stays alive. Q19a accepts this as "the app always reads the helper's output", which contradicts base assumption A1 (the helper trusts nothing about its caller). 5.3b review R-05 flagged the same class as Low; here the position (inside `-Sy`) makes it a rule-4 state, hence Medium.

#### B-01 HIGH (pass 1, confidence about 0.55: needs the one test below to confirm) A caller who ignores SIGCHLD can make the helper stop after `pacman -Sy`, leaving a partial-upgrade state, with no test failing
- Where: crates/helper/src/runner.rs:224-232 (`child.try_wait()` -> `Err(_) => return Err(RunnerError::Io)`), crates/helper/src/flows.rs:139-145 (`Err(error) => return (Err(runner_failure(error)), ...)` right after the one `-Sy`). Start checks (run.rs `start`, main.rs) look at uid, fds, cwd, argv only. They never look at signal dispositions, the blocked-signal mask or rlimits.
- Scenario: the process that starts Tidewise (a launcher, a script, a compromised app) sets SIGCHLD to SIG_IGN. On Linux an ignored disposition survives execve, and I found nothing in pkexec (which just `execv`s the program after clearing the environment and fds) that resets it. Rust's `Command` only resets SIGPIPE in the child, not SIGCHLD. In the helper, pacman exits and is auto-reaped, so the helper's `waitpid` fails with ECHILD, `try_wait` returns `Err`, the runner returns `RunnerError::Io`. In `update_job` that happens on the `-Sy` run: the helper returns an error, `-Su` never runs. Result: sync databases are newer than the installed packages. That is the exact state golden rule 4 exists to prevent (the next `pacman -S x` by the user is a partial upgrade). Same effect for a real `-S`/`-Su`: pacman finishes, the helper reports an error and skips `-D --asdeps` and the removal check. Threat-model Q16 accepted "a signal sent to the helper", but that is a root-only or terminal-only event; an inherited ignored SIGCHLD needs no signal sent and can be an accident of any launcher.
- Why no test fails: every helper test and container test starts the helper from a Rust test harness or from the shell with default dispositions.
- Proposed proving test: `tests/container/tests/helper_jobs.rs`, `an_update_still_finishes_when_the_caller_ignores_sigchld`. Start the helper with SIGCHLD ignored (no unsafe in the test crate is needed: use `/usr/bin/env --ignore-signal=CHLD /opt/.../tidewise-helper` with `arg0` handled via `exec -a`, or `setpriv`/`python3 -c signal.signal(SIGCHLD,SIG_IGN)` is not available, so env's `--ignore-signal` is the cleanest) and run an update with one pending dummy package. Assert: final line `{"finished":"ok"}`, exit 0, and `pacman -Q` shows the new version. Fails first on the exit/finished assertion. Fix options (human's call, touches crates/helper): reset SIGCHLD to default at start (rustix `process` has no sigaction; a refuse-to-start check of `/proc/self/status` `SigIgn:` and `SigBlk:` masks against an empty set needs no unsafe and no dependency), or treat ECHILD as "child gone, exit status unknown" only AFTER confirming pacman is gone and refuse before `-Sy`. Refusing at start is simplest and fits the existing "check, do not repair" style (`fds.rs`).
- Same class, same test table (also pass 1): `SigIgn`/`SigBlk` with SIGTERM/SIGHUP/SIGINT ignored (pacman then ignores them too; cosmetic), and a blocked SIGCHLD (harmless). Only SIGCHLD changes outcomes.

### 2. Seams checked

#### 2a. argv[0] check vs polkit `exec.path` vs PKGBUILD install path: sound
- One constant, `HELPER_PATH = "/usr/lib/tidewise/tidewise-helper"` (`args.rs:14`). Ties: `packaging.rs:177` builds the expected install destination from the constant; `packaging.rs:252` and `polkit_policy.rs:190` compare the policy text with the constant; the container harness has a fourth literal copy `HELPER_ARGV0` (`tests/container/tests/common/mod.rs:23`) with no compile tie (the container crate has no dependency), so a move changes three tests by constant and one by hand; the stale-literal direction fails safe (container tests fail when run).
- If one moves: path constant changes -> PKGBUILD test and policy test fail (red). Policy `exec.path` changes -> `polkit_policy.rs` fails. PKGBUILD destination changes -> `packaging.rs` fails. Container literal not updated -> container tests fail, only when run.
- Routes: typed absolute path (accepted); `..`, `.`, trailing slash, symlink name, PATH lookup resolved by pkexec, `/lib/...`, relative: all refused by the byte comparison (`summary_arg`), covered by the container rows (`package_hostile.rs:658-660`, symlink row at 1244) and `args.rs` tests. pkexec matches by `realpath`, the helper by bytes; the byte rule is strictly narrower than pkexec's, so no route is accepted by the helper that pkexec would send to the stock action (and the package test asserts `realpath(helper) == path`).
- Unbuilt: the app's launcher (M4). The helper's refusal comes after the password, so a wrong launcher shows as a refused request, not a hole.

#### 2b. Validate before summary: sound in the helper; the app side is unbuilt (C-09)
- The only caller of `summary()` in production code is `gate.rs:51`, on a request that came out of `parse_request` (which calls `validate`). `decide` has no other way to build a `Request`. Tests: `a_bad_request_gets_the_same_answer_whatever_argv_says`, `the_hostile_names_of_the_protocol_table_never_get_as_far_as_the_summary_check`. The summary binds targets, providers and the line count, not versions or the content of the confirmed list: the dry-run equality is what binds the list (flows), and a caller who supplies his own list gets exactly what that list says.
- Validate and the real run cannot disagree on names: `pacman_args::checked` re-applies the same two predicates (`is_helper_repo_name`, `is_valid_package_name`), and `flows` take the same struct.

#### 2c. `--print` list vs the real `--noconfirm` run: no divergence found beyond the known ones
- Commands: install = `-S --print --print-format '%r/%n %v' -- names` then `-S --noconfirm --ask 66 -- names`; update = one `-Sy`, then `-Su --print [-- names]`, then `-Su --noconfirm --ask 66 [-- names]`. Same names, same order (`names_of`), same db unless something else writes it.
- What can differ and what catches it: conflicts and replacements (not visible in `--print`, measured in 5.3b): the real run aborts (conflict default no) or declines (`--ask 66`), and `count_not_installed` reports a notice; file conflicts, space, integrity: real run aborts; unnamed provider: C-02; a database refreshed in the gap: C-10 (notice after the fact); flag 1 (ignored package installed anyway) is deliberately not inverted; `-d`, `--overwrite`: no field and no template (`no_command_can_carry_a_dangerous_option`, `flags_paths_and_urls_have_no_field_to_live_in`); removals: `--ask 66`, conflict default, tripwire (reports, does not prevent).
- Golden rule 4: sequences are pinned by exact `ran` vectors (`a_clean_install_runs_the_five_commands_in_order_and_ends_ok`, `a_system_update_syncs_once_compares_then_updates_without_another_sync`, `a_plain_install_never_syncs_...`); removing the dry run, reordering, or adding a second `Sync` fails them. C-01 is the one rule-4 hazard that remains.

#### 2d. Work folder vs `removal.rs`: sound; a caller cannot steer a deletion
- `/run/tidewise-helper` is root-owned 0700 under `/run` (root-only), verified by `symlink_metadata` (directory, uid 0, mode exactly 0700) before use (`workdir.rs:99-125`); files are `O_CREAT|O_EXCL`, 0600, named from the helper's own pid and a counter. A non-root caller cannot create, rename or write anything there; the only paths passed to `remove_work_file` are the helper's own two file names (`Cleanup`) and names matching `tidewise-helper-<digits>-<digits>.(out|err)` from `read_dir` of that folder, regular files only (`DirEntry::file_type` does not follow links), pid not alive. `remove_work_file` judges the spelling first (`parent == folder`, no `..`), then `symlink_metadata`, then `remove_file` (which unlinks a symlink instead of following it and fails on a directory).
- Races: the folder is checked once per job and then used by path, not by descriptor. Anyone who can swap it is root; a pacman scriptlet or hook is root, so it can do what it likes anyway (and a swap only changes where one file with a fixed name is looked for, which must exist and be a regular file). umask: set to 022 first thing (`env.rs`); the folder and files carry explicit 0700/0600 modes, so the umask cannot weaken them. A dead helper's still-running pacman may have its output file unlinked by the next helper; that only loses diagnostics (pacman keeps writing to the unlinked inode, no SIGPIPE, no lock effect).
- Rule 7 and 9 guards (`file_changes.rs`, `work_folder.rs`, clippy bans) are text and lint based: a prompt for review, as their headers say (Q25 accepted). I agree.

#### 2e. Journal fixed codes vs text from any layer: sound for the helper's own entries
- `journal.rs`: every value goes through `add_field`, which maps everything outside ` `..`~` to `?`, caps at 512 characters, and writes one `KEY=value\n` line each; `Stage::StartRefused(&'static str)` cannot take runtime text; the caller uid is a number or `unknown` (`args.rs::caller_uid`, strict digits, at most 10, fits u32); `TIDEWISE_SUMMARY` is only the recomputed summary of a validated request, whose characters are the name allow-list plus fixed words. Request text, argv, environment and pacman output never reach it. The one free-text channel in the whole helper is `Details` (pacman stderr, cleaned and capped), which goes to stdout for the app, not to the journal or to the polkit dialog (C-07 for its gaps). The polkit dialog gets only argv, which is attacker-controlled by design and accepted (Q21, option A).
- The forgeability of the journal from the outside is C-08.

Proves, as claimed: the helper's gate and jobs against real pacman 7.1.0 in a clean Arch, as root, offline (`--network=none`, `no-new-privileges`, two read-only mounts, fresh container per test file, `#[ignore]` plus `require_container()` which needs both `/run/.containerenv` and our test repo database); the package's files, modes, rpath, libraries, scriptlets and `realpath`; what pkexec hands the helper (environment, descriptors, argv, cwd) for a root caller; that 106 hostile rows are refused with the fixed code and leave `pacman -Q`, listed folders' metadata, the lock and the work folder unchanged. ### 3. Seams checked and found sound (short list)

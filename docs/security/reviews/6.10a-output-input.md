### Tests I think would survive a mutation, by importance

1. `deliver` instead of `offer` for progress. This survives the unit test `a_stdout_that_never_takes_a_line…` (fewer than 1024 lines) and the container test (A-01). Only `a_full_queue_still_delivers…` kills it.
2. Dropping `in_hand`. Survives, and the failure is timing-dependent (A-02).
3. Delete `closed` or the `Drop` impl. Survives. It is harmless because the process exits.
4. Remove the `queue.is_empty()` clause in `fits`. A line larger than the cap would then never be accepted. Probably survives, because no test sends a line larger than the cap and event lines are small.
5. Put `deliver` back for `Event::Notice` as `offer`. Killed by `a_notice_is_delivered…`.
6. `recv_timeout` replaced by `recv`. Killed by the silent-stdin tests.
7. Per-call budget instead of a shared one. Killed by `deliver_gives_up…` (900 ms against the 700 ms bound).

### Test quality notes

- Timing: the 300/500/700 ms margins and the `elapsed < 2 s` bound could flake on a very loaded CI machine. The silent-stdin container test needs at least 9 s of wall time. That is fine, but it stays a container test.
- `a_notice_is_delivered…` has a 500 ms negative check on the journal. It cannot prove ordering by itself, but the positive checks make it useful.
- Container pipe-filling: `std::io::pipe` plus a 128 KiB filler and a 300 ms sleep does give a full pipe on a default 64 KiB pipe. The reader is held open, so it is a real "never reads" case. A bare `sleep(300 ms)` is a timing assumption. Better: poll until the filler thread has finished its write.
- Test 3 (192 KiB in 100 ms chunks) proves that a slow, chunked request is accepted, not that the deadline covers the whole request. The Silent test and the unit tests cover that.

## (c) Checked and found sound

- `offer` never waits. It takes the lock for a few instructions, and the writer never holds the lock while writing.
- No lost wakeup. State changes happen under the mutex and `notify_all` comes after. `write_loop` re-checks the queue before waiting. `deliver` and `finish` re-check state in a loop, so spurious wakeups are handled.
- Budget: `OnceLock` sets the end once. `time_left` returns `None` at zero. `finish` checks `queue.is_empty() && !in_hand` before the clock. All of `deliver` plus `finish` stay inside 5 s.
- A stuck writer thread does not block exit. `std::io::cleanup` uses `try_lock` on stdout, so `main` returning calls `exit()` with a thread blocked in `write(2)`. Confirmed by reading, and the container test checks it.
- Memory: the queue holds at most 1 MiB plus one admitted line, and at most one line in the writer's hand. Progress lines are about 50 bytes, so the 1024-line cap dominates. The only 16 KiB lines are `Details`, which the helper-protocol tests check. `String` copies exist in `push` and `write_line` but are transient (at most 16 KiB each).
- `saturating_add` and `saturating_sub` are used throughout. `u32::try_from(dropped)` cannot saturate in practice. No `unwrap` in non-test code. Mutex poisoning is handled with `into_inner`.
- Exit code and journal: the exit code comes only from `outcome`. `Notes` take their values before the final line is written. The journal "finished" entry is written before the final line. The accepted entry comes before `make_runner`. `TIDEWISE_EVENTS_DROPPED` is a diagnostic only and is not part of `Notes::any()`.
- Nothing else writes to stdout. The helper only prints on stderr for start refusals.
- stdin thread: after a timeout the helper always refuses (`Malformed`) and exits. The leftover thread holds only the global stdin lock and fd 0, and pacman gets `Stdio::null()`. It does not touch the work folder, the journal or any other lock, so it cannot affect a job. A late answer is dropped because the receiver is gone. A request that arrives exactly at the deadline fails closed.
- `Stdin` (global lock, 8 KiB `BufReader`) against the old `stdin().lock()`: same buffered reader, no matter here. `take(cap + 1)` still bounds what is read.
- The stdin read happens after the start checks and before any lock, sync or pacman, so a stdin timeout changes nothing on the system.

## Findings
No High or Medium findings.

### R-01 (Low, CONFIRMED) The "any delete or replace" ban is inconsistent: `std::fs::rename` is not banned
`clippy.toml:15-28`. The new reason text says "a rename deletes the file it replaces (golden rule 7)". It bans `rustix::fs::rename`, `renameat` and `renameat_with`, but not `std::fs::rename`.
- `std::fs::rename` is not in the list, and nothing in the workspace is blocked from using it. Neither is `std::fs::hard_link`.
- The helper's only dependency on rustix is `umask`, so the rustix entries guard a path nobody uses, while the std path, which people actually write, stays open.
- Fix: add `std::fs::rename` to `disallowed-methods`, with the same "allow in one function" reason. Decide deliberately about truncating writes (`std::fs::write`, `File::create`, `OpenOptions::truncate`), which destroy a file's contents and are used in many tests, so they probably stay out. If rename stays unbanned, drop "a rename deletes the file it replaces" from the reason and from the docs, so the docs do not overclaim.

### R-02 (Low, CONFIRMED) A refused-to-start helper leaves no journal entry
`crates/helper/src/run.rs:160-166`. Start refusals return before `log`. That is consistent with the other start refusals, and it is the reason nothing from argv is leaked. But a real attempt (a symlinked start under a spoofed dialog, which only happens after the user authenticated) leaves no audit trace, unlike `summary_mismatch`, which is journaled.
- Fix, optional: write one fixed-text journal line for `WrongProgramPath` only, with no argv content. Otherwise state in the threat model that start refusals are not journaled.
- Related: the `pkexec_uid` line in `args.rs` says the id goes into the log, so keep any new entry free of argv.

### R-03 (Low, PLAUSIBLE) The new source-guard in `work_folder.rs:151-181` has two blind spots and a theoretical false positive
- Blind spot 1: `line.starts_with(' ')` allows everything indented. After the first marker, a second `impl WorkDir {` at column 0 is allowed (workdir.rs only). A production `pub fn` could then be added inside that block, without `#[cfg(test)]`, and the guard would not see it.
  - The existing test `the_test_only_constructor_sits_alone_before_the_unit_tests` (work_folder.rs:~125-139) is the only other defence. I read it but did not prove it catches this case.
  - Fix: allow `impl WorkDir {` only when the previous non-blank line is `#[cfg(test)]`, or only once.
- Blind spot 2: a column-0 `mod tests {` and a column-0 `}` are accepted anywhere after the first marker. That is sound under rustfmt.
  - `#[rustfmt::skip]` or an unformatted file would fail the guard loudly (an unlisted column-0 item such as `fn x()` trips it), not silently.
  - A multi-line string or raw string with column-0 text inside a test would be a false positive. None exists today.
  - If a false positive appears, the escape hatch is to indent the literal or use `concat!`. The comment should say so, so nobody weakens the guard.
- `split_once("#[cfg(test)]")` takes the first occurrence of the text anywhere, including inside a comment or string. No production file has one before its real marker today. A comment with that text would make the guard read more than before, so it fails loudly, not silently.
- `src_has_no_subfolders` is sound, and `lib.rs` module declarations after the marker are fine because each module's own file is read.

### R-04 (Info, CONFIRMED) The polkit container tests cannot show which action pkexec matched
`tests/container/tests/polkit.rs`. As root, pkexec is authorized whatever the action, so the symlink and PATH tests prove only what argv[0] the helper received and that it refused or accepted. They do not prove `find_action_for_path` selected our action. The header says this honestly. Keep that sentence; do not let anyone cite these tests for "pkexec matches `exec.path` by realpath".

### R-05 (Info, CONFIRMED) Leftover state after a failed container test
`polkit.rs`, premise test and symlink test. `fs::remove_file(&link)` and `fs::remove_dir(folder)` run at the end of the test body, not in a `Drop`. A failed assertion leaves `/tmp/NO PASSWORD NEEDED, press Cancel/...` behind.
- Later tests in the same container would then fail on `symlink()` with `AlreadyExists`, but only for the same link name, and each test file gets a fresh container. The premise test uses `bash` as the link name and the symlink test uses `tidewise-helper`, so they do not collide with each other.
- `InstalledHelper` and `Polkit` clean up in `Drop` and are fine.
- `reset_world` runs at the start of each of the three pacman tests, so package state does not leak between them. `reset_world` also removes dummy packages first, so `installed_version(...) == None` in the symlink test is meaningful.
- Fix, optional: put the link and folder in a small `Drop` guard.

### R-06 (Info) Development builds cannot use pkexec at all, and now not the other path either
Not a defect. The policy already pins the real path, and the helper now also demands it. Anyone testing from `target/` or `/opt` has no pkexec route. The container tests solve this with `arg0` or `exec -a`. Document it for contributors.

## Checked and found fine
A. argv[0] check
- `summary_arg` (`args.rs`) compares bytes with `as_bytes()`: no normalising, no `Path`, no UTF-8 conversion. Count is judged first (`(Some, Some, None)` pattern), then path.
- The order in `start()` is root, then fds, then chdir, then argv, all before `read_capped(stdin)` and before any journal write. The new test `the_program_path_is_checked_last_and_after_the_count` proves the order.
- The refusal text is one fixed sentence. Nothing from argv is repeated or logged (`a_wrong_program_path_is_never_repeated`).
- Legitimate starts still work: `pkexec /usr/lib/tidewise/tidewise-helper <summary>` and a PATH lookup of `tidewise-helper`, which arrives absolute. Both are covered by container tests, which I did not run.
- `--keep-cwd` and `--user root` only appear before argv[n], so they do not change argv[0]. `--user someone-else` fails the existing NotRoot check. An `env`/`sudo`/`flatpak-spawn` wrapper changes argv[0] and is refused by design.
- No normalisation edge case slips through. `./x`, `//usr/...`, a trailing slash, `..`, a PATH element such as `/usr/lib/tidewise/../tidewise` all differ as bytes and are refused. A relative PATH element that resolves to exactly the string `/usr/lib/tidewise/tidewise-helper` is the real helper and harmless.
- pkexec's `execv` target is `realpath(typed path)`. If argv[0] equals the fixed path, the program executed is whatever that path resolves to. Only root can change that.
- Residual that stays: the attacker still controls argv[1], so a spoofed dialog still shows attacker text after the fixed sentence and path. The helper refuses after authentication (summary mismatch). The argv[0] check does not change that, and the threat model must keep saying so.
- argv[0] is not an identity proof. A root process can `exec -a` anything. The check is dialog-integrity hardening only.
- `fuzz/` does not call `summary_arg` or `Facts` (checked `fuzz_targets` and `fuzz/Cargo.toml`). `crates/helper/tests` do not pass their own argv to the helper except `not_root.rs`, which stops at NotRoot (the root check runs first, so argv is never reached). `run.rs`'s own `good_facts` was updated. `polkit_policy.rs` has the new test tying the policy `exec.path` to `HELPER_PATH`.

# Independent review: 5.3a helper gate (branch `feat/helper-gate` against `main`)

## Scope and method

Read: `docs/security/threat-model.md` (and its 5.3a diff), decision 0005, `CLAUDE.md` golden rules, every file in
`crates/helper/src/`, `crates/helper/tests/not_root.rs`, the `crates/helper-protocol` diff plus `summary.rs`,
`parse.rs`, `validate.rs`, `tests/container/run.sh`, `tests/container/README.md` diff and
`tests/container/tests/helper.rs`.

Ran: `cargo test --all` (all pass), `cargo clippy --all-targets -- -D warnings` (clean), a script that checked
that every snake_case test name cited in the threat-model diff exists as a `fn`, and the debug binary as the
ordinary user (plain, and under `unshare -r`, always with no argument so it exits before it could log).
Not run (as instructed): podman, `run.sh`, fuzzing, pkexec. So **no container test was executed by me**; I read them.

**Result: no High or Medium issue in the 5.3a code as it stands.** The helper in this PR has no path to a child
process, shell, file write or caller-chosen file, and I found no panic path. There is one Low finding that becomes
a Medium-class design issue in 5.3b (R-01), and several Low/Info items.

## Findings

### R-01  Low (carry to 5.3b as Medium)  CONFIRMED: "root" is decided from `/proc/self/status`, so a user-namespace "root" passes

`crates/helper/src/uid.rs` (`effective_uid`, `is_root`, `read_status`), used in `run.rs` `start()`.

Scenario: an ordinary user runs `unshare -r target/debug/tidewise-helper` (no pkexec, no polkit, no password). Inside
the new user namespace `/proc/self/status` shows `Uid: 0 0 0 0` (it is rendered in the reader's namespace), so
`is_root` is true. I reproduced it: with no argument, the plain run prints "must be started as root through pkexec"
(exit 2), while the `unshare -r` run gets past the root check and prints the *later* "exactly one argument"
refusal (exit 2). `/proc/self/uid_map` there is `0 1000 1`.

Impact today: none. The fake root has no real privilege and the 5.3a code only parses and logs (the journal
socket is world-writable, so it can already be reached by anyone; journald stamps the real `_UID`). Impact in 5.3b:
the root check is documented as the thing that stops "run the helper without pkexec" (T-01); it does not. Anything
that later depends on "we are really root" (for example a trust decision, or logging `PKEXEC_UID` as meaningful)
would be wrong in a namespace, and the user controls the mount namespace there too, so they can also show the helper
a fake `/proc`, fake `/var/lib/pacman`, etc.

Fix: additionally require `/proc/self/uid_map` to be exactly the identity mapping of the initial namespace
(`0 0 4294967295`, whitespace-normalised). That is safe Rust (read a file). Add it to the unit tests (`uid_map` as an
argument) and one container test. Also say in the threat model that the check is "not a user namespace", not
"uid 0". If the human decides it is not worth it, record in T-01 that the root check is a guard against
accidents, and that privilege comes only from pkexec/polkit.

### R-02  Low  CONFIRMED: `nothing_on_the_system_changes` watches only five trees

`tests/container/tests/helper.rs:~170-195` (`snapshot`) and `:498` (the test).

It records metadata of `/etc /usr /var/lib/pacman /var/cache/pacman /var/log` (and `pacman -Q`, and the lock file).
A helper that wrote to `/root`, `/tmp`, `/opt`, `/srv`, `/var/tmp`, `/home`, `/boot` or `/run` would pass. `/tmp` is
even used by the flock test. Compare is on size, mode and mtime only (a same-size, same-mtime rewrite would pass; unlikely).
The claim in the doc comment, "everything under the folders where a helper could do harm", is a judgement, not a proof.

Fix: walk `/` minus `/proc /sys /dev /run /tmp` (and those separately for new entries), or add `/root /opt /srv
/var/tmp /boot /home`. Name the exclusions in the test.

### R-03  Info  CONFIRMED: the threat model cites a test name that no longer exists

`docs/security/threat-model.md`, T-02 row: `chosen_providers_are_listed_when_all_of_them_fit_and_left_out_when_not`. The
commit `bceb984/ee72828` renamed it to `chosen_providers_are_listed_when_all_of_them_fit_and_counted_when_not`. Every
other snake_case test name in the 5.3a diff of the threat model exists (checked by script); the only other misses were
non-tests (`env_clear`, `auth_admin`, `allow_any`, ...). Fix: update the old name in the "Protocol side (5.2)" sentence.

### R-04  Info  CONFIRMED (by design): with 2 or more providers cut from the summary, the user sees only a count

`crates/helper-protocol/src/summary.rs`, `counted_providers`, `install_text`.

The 200-byte cap holds for every input: the room for ` and K more`, ` with N providers` and ` (N packages)` is reserved
before each target is added (`ending` at line ~44), so after the last listed target `text + counted + total <= 200`
holds, and the provider loop only names a provider when `text + with + 1 + word + total <= 200`. No underflow:
`count - index - 1` has `index < count`; `count - shown` has `shown < count`. Provider/target counts are capped at 100
by `validate` before `summary` runs, and `summary` is also safe on unvalidated input (`ascii()` takes at most 200
chars). Remaining weakness: when names do not fit, a request that picks provider A and one that picks provider B read
the same (`with 1 provider`); the same is true for requests that differ only past a cut target list and for the
`dependency` field of an answer, which is never shown. This is documented as a known limit; the confirmed list (T-09)
is the real check in 5.3b. No fix needed now; just do not describe the summary as identifying the request.

### R-05  Info  CONFIRMED: T-08 and golden rule 3 promises are not yet in code (fine, but nothing enforces them yet)

`crates/helper/src/main.rs`. The row says the helper does `env_clear + LC_ALL=C`, `chdir("/")`, `umask 022`. Only the
`chdir` exists; there is no umask call (impossible without unsafe or a dependency, std has no `umask`) and the process's
own environment is not cleared (it only reads `PKEXEC_UID`). In 5.3a there are no files and no children, so this is
harmless. For 5.3b: children get `env_clear()`, and the umask question needs a decision (a dependency, a pacman
`--` default, or documenting that pkexec's umask is relied on). The T-08 "Status" cell should not read as done.

### R-06  Info  CONFIRMED (documented): a caller that keeps stdin open and silent holds the process; the journal send can block up to 2 s

`crates/helper/src/input.rs` (`read_capped` has no timeout) and `journal.rs::send` (2 s write timeout; the connect-less
`send_to` on a datagram socket can still block when the receiver queue is full). Harmless in 5.3a (nothing is held;
the caller needs a polkit authorisation to start it). The input.rs comment already says the whole request must be read
and validated before any lock in 5.3b. Keep that as a hard rule for the 5.3b plan.

**Closed on the stdin half (6.10a, 18 Nov 2026; review 5.8 R-04, question 34).** The "harmless" reading was too kind: the real harm of a silent stdin
is an already-approved helper that is parked and released later. `input::read_within` now gives the whole request 10 s
(`InputError::TimedOut`, refused as `Malformed`); container `a_silent_stdin_gives_up_after_the_deadline`. The journal-send half (up to 2 s) is unchanged.

## Checked and found sound

- **No child process, shell, file open or write.** `grep` over `crates/helper/src` finds no `Command`, `File::`,
  `OpenOptions`, `write(` to a path. The only I/O: read `/proc/self/fd`, `/proc/self/status`, stdin, one `send_to` to a fixed
  `/run/systemd/journal/socket`, stdout, stderr. `forbid(unsafe_code)` is in both `lib.rs` and `main.rs`.
- **Nothing the caller says reaches a path or command.** argv[1] is kept as raw bytes (`OsStringExt::into_vec`, so
  non-UTF-8 does not panic) and is only compared byte for byte with the recomputed summary. `PKEXEC_UID` is a digits-only,
  at most 10 characters, `u32`-parsed number or `unknown`.
- **Ordering of the start checks.** fds, then effective uid, then chdir result, then argv count; stdin is only read after
  all four pass; verified by the `Watched` unit test and by the not-root real-binary test. `chdir("/")` before the root
  check is harmless. Failing to read `/proc/self/fd` or `/proc/self/status` refuses (fail closed). Two `Uid:` lines or
  any malformed field refuse. A `Name:` line cannot forge a `Uid:` line (the kernel escapes newlines in `Name`).
- **Summary comparison.** Parse and validate first, then compare the recomputed summary with argv bytes; a request that
  fails validation never reaches the comparison, and neither argv nor stdin text is echoed to stdout, stderr or the
  journal (stdout carries an error code only; the journal gets the recomputed summary only for a valid request).
- **stdin cap.** `take(MAX + 1).read_to_end` bounds memory at 2 MiB + 1; `parse_request` refuses `> MAX` before parsing;
  `u64::try_from(..).saturating_add(1)` cannot overflow. Non-UTF-8 and NUL give `malformed` through serde; a second
  loose parse only reads `protocol_version`. Nesting: `deep_nesting_is_refused_and_does_not_overflow_the_stack` is cited
  and exists. Collections after parsing are bounded (100 targets, 100 providers, 5 000 transaction lines, names <= 128).
- **No panic path found.** `deny(unwrap_used, expect_used, indexing_slicing, panic, print_*, dbg_macro)` outside tests,
  clippy clean. Arithmetic is on small bounded values. `write_line` returns the error and `run` ignores it on purpose;
  Rust ignores SIGPIPE so a closed pipe is `EPIPE`, and a closed fd 1/2 is tolerated by std; `/dev/full` gives `ENOSPC`.
  The container tests for full/gone stdout and stderr read correctly (`101` would be a panic). No allocation grows with
  caller input beyond the 2 MiB cap.
- **Inherited fds.** Fooling the check with a leaked fd whose target is `/proc/<pid>/fd` does not work: the helper's own
  directory descriptor is always in the list, and only one listing entry is tolerated, so the leaked one plus the real
  one gives `Unexpected`. Look-alikes (`(deleted)`, trailing `/`, other pids) are refused and tested. Any error while listing
  refuses. It is stated as a second line of defence behind pkexec's close-on-exec (source 16, which I could not open).
  Fds 0 to 2 are not inspected at all: stdin/stdout/stderr may be any file the caller could open, but the helper only
  reads at most 2 MiB from stdin and writes one fixed line, so no content or path is exposed.
- **Journal datagram.** Every value goes through `add_field`: only `' '..='~' `, everything else (newline, NUL, ESC,
  non-ASCII, direction marks) becomes `?`, 512 chars max, so no extra line or field and no binary-encoded value; the
  keys are constants and none starts with `_`; the longest datagram is well under 2 KiB (no `EMSGSIZE`). The socket path
  is a constant in a root-owned directory; the sender is unbound (no filesystem artefact); a failed or cut send is
  ignored for the outcome. Order: log, then stdout.
- **summary() cap and arithmetic.** See R-04; reasoned through the loop for 0, 1, many targets, all-cut,
  first-target-too-long (`" ..."` case adds 4 bytes but the long word alone cannot fit, so the text stays far below 200),
  and 100 000 providers (test exists, and validation caps it at 100 anyway).
- **Container harness.** `run.sh` still refuses root, requires rootless podman, uses no `--privileged`, `--network=none`,
  adds `--no-new-privileges`, and mounts only the test binary and the helper, both `:ro`; one fresh container per
  test file. `realpath` resolves symlinks before mounting. I see no path from a container test to the host.
- **Hostile-input test construction is not vacuous.** The `replace()` fixtures (`protocol_version`, `"name":"glibc"`)
  would give a *valid* request if the pattern did not match, and the assertions (`version_mismatch`, `invalid`) would then
  fail, so a wrong pattern cannot pass silently.
- **Golden rules.** The app is untouched; the helper has no actions (rule 2 not widened beyond the new `NotImplemented`
  error code, which is an output); no pacman call (rules 4, 9, 10 not engaged); no network.

## Claims I could not verify

- That the container tests pass (`an_inherited_file_descriptor_is_refused_to_start` relies on `flock(1)` leaving fd 3
  open, and on `/usr/sbin/flock` being in the image). I read them; I did not run podman.
- That pkexec marks every fd >= 3 close-on-exec and passes only `PKEXEC_UID` and a minimal environment (threat-model
  sources 16 and 18). Not checkable offline; the helper does not depend on it for correctness beyond defence in depth.
- That `LD_PRELOAD` and similar are harmless under real pkexec (the tests say so and do not test it; planned for 5.4).
- The 10-minute fuzz claims for the `request` target (not rerun here).
- Behaviour under a PID namespace where the `/proc` mount is for another namespace: the fd listing would show a
  different pid, and the helper would refuse (fail closed). Not tested.

## Findings

### R-01 (Low, CONFIRMED) A skipped check is invisible to the app; only the journal says so
`crates/helper/src/flows.rs` `compare_lists` (about lines 275-305); `run.rs` test `a_removal_check_that_could_not_run_is_logged_as_skipped...` asserts `!stdout.contains("notice")`.
If either `pacman -Q` list is unreadable, stdout carries no notice and the final line is `{"finished":"ok"}`. The app (the person at the screen) sees a clean success. Same for the not-installed check: it is now dropped silently when the AFTER list is unreadable (the old `post_check` also dropped on error, but only for exit codes other than 0/1). The human's rule ("a check that did not run must never be logged like a clean pass") is met for the journal only. Scenario: a broken local DB entry makes the AFTER `-Q` fail; a package has vanished; the user is told "ok".
Fix: add a fixed-text notice (for example `Notice::RemovalCheckSkipped`, no count) or document in the threat model that the app deliberately cannot tell. This needs the human's OK (protocol change).

### R-02 (Low, CONFIRMED) "Complete list" is claimed, but stderr is ignored and exit 0 can hide skipped entries
`flows.rs` `read_installed_list`. The author's own spike (commit message of the container-tests commit) found that an empty entry directory or a `desc` file without a name makes `pacman -Q` exit 0 and silently skip the entry. The code accepts exit 0 with any stderr. Scenario: a damaged entry present in the BEFORE list's database but repaired or damaged differently AFTER shows as removed or hides a real removal. Also a list that parses to zero packages (exit 0, empty stdout) counts as `Done` with 0 removed, a vacuous pass. Every Arch system has at least `pacman` in `-Q`.
Fix: treat a list as unreadable if stderr has any line starting `error:` or if it parses to no packages (cheap sanity: it must contain `pacman`). Add unit tests for both.

### R-03 (Low, PLAUSIBLE) A read error while capturing is treated as end of output, not as a cut list
`runner.rs` `Capture::drain`: `Ok(0) | Err(_) => return`. Only the byte cap sets `truncated`. If a read of the stdout file fails (EIO) partway, `pacman -Q` exit 0 gives a short list with `truncated == false`, and a short AFTER list turns into a large false "N packages were removed". Very unlikely on the tmpfs work folder, but the code comment promises completeness. Fix: set a `read_failed` flag (or `truncated = true`) on `Err` and let `read_installed_list` reject it.

### R-04 (Low, PLAUSIBLE) `RunnerError::Io` after pacman has started is reported as "not run"
`runner.rs` `run_program` returns `Err(Io)` from `try_wait` / `wait` failure with the child possibly still running; `flows.rs` `real_run_and_after` maps any `Err` from the real run to `Counts::default()` (`NotRun`, no journal field, no comparison, helper exits while pacman continues in its own group). Practically unreachable, but then the removal check silently does not exist for a transaction that may have run. Fix: for `Io` (not `Spawn`/`WorkDir`/`Args`) mark `Skipped` or still try the AFTER list.

### R-05 (Low, CONFIRMED) The unit test cited as proof for `ListInstalled` having no `--` is vacuous for it
`pacman_args.rs` `every_package_goes_after_the_double_dash`: `names_given = !matches!(..ListInstalled..) || built.contains("--")` is false for `ListInstalled`, so nothing is asserted. T-04 cites this test. What actually proves the point is the exact-argv test `the_exact_argument_list_of_every_command` (`["-Q"]`) plus `all_commands()` containing `ListInstalled`. Fix: assert `!built.contains("--")` for the commands that take no names, and cite the exact-argv test in T-04.

### R-06 (Info, CONFIRMED) Stale text
- `output.rs:91` and `:123` doc comments still say "stdout of `pacman -Q -- <names>`" (command removed).
- T-14 row still says "PRIORITY (6 for accepted and for a finish with ok, 4 for every refusal or failure)"; now only a clean ok is 6 and an ok with notes is 4 (the 5.3c text follows, so the row contradicts itself).
- Decision 0006 and README are consistent; the 5.3b review file mentions the old command historically (fine).

### R-07 (Info, CONFIRMED) Container test hygiene
- `tidewise-dummy-remover` deletes the victim's DB entry but its files stay in `/usr/share/tidewise-test/`; `reset_world` removes dummies via `pacman -Rdd` by name, so the victim's files are orphaned. A second run of that test in the same container (retry, or any later test installing the victim) would hit "exists in filesystem". Only one test uses the victim today, and run.sh uses a fresh container per file.
- `reset_world` restores `ALPM_DB_VERSION` BEFORE `local_repository_only()` and before its `/tmp/tidewise-*` sweep deletes the backup, so the order is right, and the breaker test restores the file immediately after `run()`. Robust enough; a panic inside `run()` is covered by the next `reset_world`. If `cp` of the backup ever failed in post_install the test would still delete the version file (no backup) and all following pacman commands fail: add `set -e`-style check or copy with a fallback.
- Tests share state and rely on `--test-threads=1` (run.sh line 72); fine.

### R-08 (Info) Journal absence of a field is ambiguous on errors only
For `ok` outcomes the cases are exact: no field means the check ran. For error outcomes no `TIDEWISE_REMOVAL_CHECK` can mean `Done` or `NotRun` (and R-04). Acceptable; say so in T-14.

## What the check cannot see (state in the threat model)
- A package removed and installed again under the same name (versions are not compared; this is by design, a downgrade is Q18).
- Anything done with root by a hostile scriptlet: it can edit the local DB (`/var/lib/pacman/local`) and forge a missing or extra entry in either list, or hide a removal. Documented in T-18 as "tripwire, not proof".
- Removals by another process between the two reads (another pacman run by the user, no lock is taken by `-Q`): attributed to this job (false positive), or a concurrent partial DB write read as a removal.
- Files deleted that are not whole packages; user files.
- Replacements declined (`--ask 66`) never reach the check because nothing is removed.

## Checked and found sound
- Argv: `ListInstalled` is `["-Q"]` fixed, no `--`, no names; `VerifyInstalled` is gone from code, tests, fuzz; no template can yield `-Q -- <names>` (`grep` of `VerifyInstalled` finds nothing outside docs history). `name_only` is only used by `MarkAsDeps`. Runner: `timeout_for(ListInstalled) == Some(READ_TIMEOUT)`, tested in runner.rs.
- No request value or package output reaches the lists: both lists come from separate `pacman -Q` runs, stdout of the real run is only fed to the progress parser; a scriptlet printing "removing x..." cannot create a notice.
- Count parsing: `u32::try_from(len).unwrap_or(u32::MAX)`, HashSet use is linear, `removed_names` dedups, noise lines ignored the same way in both lists, versions ignored, new packages ignored. 5 000-line lists tested; STDOUT_CAP 4 MiB is far above a real `-Q` (about 40 bytes per line); a cap-hit sets `truncated` and the list is rejected (tested).
- Unreadable rules: exit 1, exit 2, timeout, truncated, spawn error all give `Skipped` (unit tests for before and after). Partial list from an exit-1 run is not trusted (tested).
- Ordering: BEFORE is read after the dry run and the lock look; if the real run cannot start nothing is compared (`no_real_run_means_no_removal_check`); a failed real run is still compared, which is right (partial progress can remove). Provider marking now depends on the BEFORE list exactly as before (installed providers not marked; unreadable list marks nothing).
- Journal: all values are numbers or the fixed text `skipped`; `add_field` also filters to printable ASCII; field order fixed and tested; clean ok unchanged (PRIORITY 6, no new fields); errors keep their code and get fields; `ok_with_notices` only for `Outcome::Ok`. `run.rs` order: notices during the job, then journal finished entry, then the audit notice, then the final line.
- Golden rules: 2 (allow-list: the change narrows it, removes one read with names and adds one read without; the human approved with the plan per T-04 text), 3, 5, 8, 9 (no touch of db.lck; the breaker test removes `ALPM_DB_VERSION` only inside the container), 10 (no new flags).
- Fuzz target properties are sound (self diff empty, reported names were listed and are not still listed, each once, empty after-list gives all unique names).
- Cited test names all exist (see Scope).

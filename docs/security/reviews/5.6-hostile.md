## Findings

### R-01 (Medium, CONFIRMED) The environment, descriptor and pkexec-refusal rows test pkexec, and the table's own mutation shows it
Where: `package_hostile.rs:597-712` (`env_rows`, the `fd` row, the seven `pkexec refuses` rows), `judge_environment` (1052-1097), threat model T-08 ("Through real pkexec (5.6)") and Q31.

What: 13 env rows end in `summary_mismatch` with a wrong summary. They show that pkexec hands the helper a scrubbed environment (measured, good), and that the helper's gate then answers. Nothing in them depends on how the helper treats its environment: the helper reads only `PKEXEC_UID`, which pkexec has already overwritten (R-06). No job runs, so the helper's `env_clear` + `LC_ALL=C` for children, the absolute `/usr/bin/pacman`, `umask`, signal handling and stdin of children are not reached by any row. The 7 `pkexec refuses` rows are pkexec exiting 127 before the helper exists. The author's own third mutation (fd check off) leaves the `fd` row green because pkexec closes the descriptor first.

Evidence (what would stay green):
- Helper's `/proc/self/fd` check removed or loosened: green (author's mutation; only the direct-start container test `an_inherited_file_descriptor_is_refused_to_start` from 5.3a catches it).
- `chdir("/")` removed from `main`: green. pkexec starts the helper in `/root`; `run_row` sets `current_dir("/")` only for pkexec, and nothing reads `/proc/<pid>/cwd`. T-08 lists the working directory.
- `umask 022` dropped, signal mask changed: green (not read; `/proc/<pid>/status` has `Umask:` and `SigBlk:`/`SigIgn:`).
- Helper starts honouring `PACMAN_ROOT`, `LC_ALL` or `HOME` from its environment for the children it will start: green (no child is ever started).
- Env scrubbing disabled in pkexec itself (a different polkit build): red, which is the point of measuring it, but it is a test of polkit.

Why Medium: T-08 and the 5.6 commit message read as "the helper is proven against a hostile environment and an inherited descriptor through the real pkexec". What is proven is "pkexec does not pass them on, in this polkit version, to a root caller". That is useful (it is the premise of the helper's design) but it is not the helper's defence, and the text should not let the human count the rows as such.

Recommendation:
1. In the `inspect` rows also read `/proc/<pid>/cwd` (expect `/`) and the `Umask:` line of `/proc/<pid>/status` (expect `0022`). Both are cheap, run while the helper waits for stdin, and cover the two T-08 items that sit before the gate. Do not add helper code for this.
2. In T-08 and Q31, say in one sentence: "these rows measure what pkexec passes on; the helper's own descriptor check is proven only by the direct-start container test (pkexec closes the descriptor first; mutation check 5.6), and its child environment only by the 5.3b job tests."
3. Optional: a `fd` row variant that leaks an fd that pkexec does not close is not possible with pkexec; leave it, but record it in the checklist as "cannot be tested through pkexec".
Needs a human decision: no (test and wording only).

### R-02 (Low, CONFIRMED) Hostile values go into one place of one action; no row reaches a job; no "invalid request plus wrong argv" row
Where: `World::with_name` (148), `with_repo` (156), `with_version` (164); `table()`.

What: the request is always the `install` fixture (`install_hello`). A hostile name or repository replaces only the **first target**; a hostile version replaces only the **first confirmed line**. Never hostile through pkexec: `providers[]`, `transaction[].name` / `.repo`, a second target, the `update_system` and `update_system_and_install` actions, duplicates, 100+ providers, 5 000+ confirmed lines. T-06 says the protocol side is covered "everywhere a name can go" by unit tests, which is true; the 5.6 text ("26 hostile package names ... each `invalid`") is accurate but is one position.

Also absent:
- No row sends an **invalid request together with a wrong summary** (the `a_bad_request_gets_the_same_answer_whatever_argv_says` property, T-02 "validation first so argv cannot be used to probe"). A helper that compared the summary before validating would fail the name rows (they carry the original request's summary, so they would get `summary_mismatch` instead of `invalid`), so that reordering is caught for names; a check that looks only at argv (empty, length) before parsing is not, because no row combines a bad request with a bad argv.
- No row reaches a job, so golden rules 4, 5, 8, 9 and 10 are not exercised through pkexec by this test (they are in the 5.3b container tests, run directly). The title "end to end" should read "the gate, end to end".
- There is no positive control inside this test (a valid request with the true summary going all the way through the same `run_row`). `package.rs` has a real job through pkexec, so the harness is known to work; the table itself would stay green if, say, `run_row` always built the wrong argv, because most expectations are refusals. The exact-output checks make this unlikely, not impossible.

Weakenings the table does **not** catch, with the nearest row (none unless stated):
- Summary compared after `trim_start()` only (the `+ " "` row catches trailing trim, none for leading); compared with `eq_ignore_ascii_case` (the capitals row catches it); compared as a prefix either way (empty row and `+ " "` row catch it).
- Version validation dropped for a position other than the first line.
- A name rule dropped in the helper but kept in the protocol: not applicable, the helper has no copy (one copy in `tidewise-names`), so a drop in the protocol is caught by the name rows for `targets[0]` only.
- Request cap raised: caught by `size: ... + 1` (the padded valid request would be accepted and install the dummy). Cap lowered below 1 MB: caught by the 1 MB name row (`too_large` instead of `invalid`). Cap changed by a small amount downward: not caught (the constant in `common` is a copy, see R-07).

Recommendation: add `invalid request + wrong summary` for one row, one hostile name in `providers` and one in `transaction`, and one `update_system` request with a bad version; retitle "gate". All are small `Row::new(...).stdin(...)` lines. Needs a human decision: no.

### R-03 (Low, CONFIRMED) "Reaches the helper unchanged / byte for byte" is not what the rows show
Where: threat model Q21 ("Measured in 5.6": "an `argv[1]` that is not UTF-8 reaches the helper byte for byte (the helper answered `summary_mismatch` for it)"; "Markup, new lines, 200 lines, 20 KB ... reach the helper unchanged and are refused there"), T-02.

What: the helper never reveals argv (by design: the journal holds the recomputed summary). `summary_mismatch` is the answer for the original bytes **and** for any altered bytes (U+FFFD substitution, truncation, a stripped new line). So the rows prove "whatever arrived was refused and not repeated". They do not prove what arrived, which is what the dialog question (Q21) cares about: pkexec's GLib warning on stderr (checked) suggests the string is dropped from the details it sends to polkit, which is a different fact from "reaches the helper unchanged".

Evidence: `judge` never sees the argv bytes the helper received; no row sets `inspect` for the argv rows.

Recommendation: either soften Q21 to "is refused with `summary_mismatch` and is not repeated", or make the argv rows `inspect` rows and compare `/proc/<pid>/cmdline` (NUL-separated `argv0\0argv1\0`) with what was sent. The second is about ten lines and turns the claim into a measurement. Needs a human decision: no.

### R-05 (Low, CONFIRMED) "Nothing changed" is narrower than its sentence
Where: `common/mod.rs:234-268` (`snapshot`), `package_hostile.rs:1137-1155`.

What the check is: `pacman -Q` list, then metadata (size, mode, mtime sec and nsec) of everything under the eleven roots listed above, compared after each row, plus `db.lck` exists and `/run/tidewise-helper` exists. What it cannot see:
- Anything under `/run` (the work folder is checked by name only, after the row), `/dev`, `/proc`, `/sys`, `/var/lib` other than `pacman`, in particular `/var/lib/polkit-1`, `/var/tmp`, `/var/spool`, `/mnt`, `/media`, `/lib` (a symlink; `symlink_metadata` does not follow it, `/usr` covers the target).
- Content changes that keep size, mode and mtime (a helper could, in principle, `utimes` back; unlikely, but the claim is "unchanged", not "metadata unchanged").
- A work folder created **and removed** inside the same row (the helper's own cleanup runs before the helper exits). The post-hoc `exists()` misses it; the `/var/lib/pacman` directory mtime does catch a lock created and removed there, so the lock side is covered, the work-folder side is not. This is the property T-07 names ("read and validated before the work folder is made"); it is proven by the 5.3b test `a_refusal_never_creates_the_work_folder_or_starts_pacman` with the same limitation, and by code order.
- `differences(..)` stops at 10 paths (only a readability limit).
Recommendation: say "metadata under these folders" in the header and T-01; optionally add `/run`, `/var/lib/polkit-1` and `/var/tmp` (the `FakeJournal` creates and removes `/run/systemd` per row, so `/run` would need an exclusion). A transient work-folder check would need an inotify watch on `/run` started before the row; I would not add that for 5.6, only state the limit. Needs a human decision: no.

### R-06 (Low, CONFIRMED) The helper never sees a forged or non-zero caller id here
Where: env rows "PKEXEC_UID forged as 77", "... with a new line", every journal comparison (`TIDEWISE_CALLER_UID=0`), `entry()`.

What: pkexec sets `PKEXEC_UID` itself (the row asserts it is `0` in `/proc/<pid>/environ`), so the helper's `caller_uid` is always given `0`. Consequences: (a) the rows say nothing about how the helper handles a hostile `PKEXEC_UID` (that is `caller_uid`'s unit tests, `a_hostile_pkexec_uid_is_logged_as_unknown_in_both_entries`, and the `gate` fuzz target); (b) a change that made the helper trust or branch on the caller's uid (for example "uid 0 may skip the summary check", or a different path for uid != 0) cannot be caught, since every row is uid 0; (c) the "valid request from another uid" statement is correctly **not** claimed. T-14 ("a forged `PKEXEC_UID` never reaches it") is true and is a statement about pkexec.
Recommendation: one sentence in T-01 and Q31 ("the journal's caller id is always 0 here; a non-zero value, and the helper's handling of a hostile `PKEXEC_UID`, are covered by unit tests, the `gate` fuzz target and VM checklist item 1"). Checklist item 1 already requires `TIDEWISE_CALLER_UID=<uid>`; keep it. Needs a human decision: no.

### R-07 (Low, CONFIRMED) Harness details that can hide a regression or make a row vacuous
1. **EPIPE tolerance** (`may_break_the_pipe`, 236-239): any row with `stdin.len() > 60_000`, and every `StartRefused` and `PkexecRefused` row, may fail the write with a broken pipe. The 8 MiB row therefore passes whether the helper stops at cap + 1 (what T-07 claims, `read_capped`) or reads all 8 MiB and then answers `too_large`. "Reads at most cap + 1 bytes" is proven only by the 5.3a unit tests. Not a bug in the test; say so in T-07's 5.6 text, or assert (on the 8 MiB row only) that the write **did** fail, which a helper that drains stdin would not do.
2. **The leaked descriptor is never shown to reach pkexec.** The fd row passes if `flock(1)` had closed the descriptor (for example an `-o` flag, a different util-linux, or a close-on-exec lock fd). `spike.out` measured it once; the row does not re-assert it. Check `/proc/<pkexec pid>/fd` in the same row, or state that the leak is a spike measurement.
3. **Finding the helper** (`find_helper`, `settled_helper`): matches any process whose `exe` equals the installed helper, polls every 5 ms for 10 s. Races are not a source of false passes: no helper found, an unreadable environ or fds, or an empty environment all become problems (`could_not_find_the_helper`, "could not be read"); `settled_helper` needs two equal, non-empty reads 30 ms apart while the helper blocks on our open stdin. A stale helper from the previous row cannot exist (`wait_with_output` returns after `timeout` and pkexec exit). One theoretical false pass: two reads agreeing on a state that is not yet final cannot happen because the helper is blocked, and a row whose helper has already exited reports "not found", loudly. Fine.
4. `Row::needle` only keeps text of 4 to 200 bytes (`-dd`, `--`, `*`, `-x`, `a;b` and the NUL name are skipped); the exact-stdout and exact-journal comparisons make the needle redundant for `Refused` rows, so no gap, but "the hostile text is searched for in stdout, stderr and the journal and never found" (T-15 5.6) covers fewer rows than it sounds like, and not the 20 KB argv row, which is over 200 bytes (the whole entry is compared there, which does the same job).
5. `MAX_REQUEST_BYTES` in `common/mod.rs` is a copy of the protocol constant. If the protocol's cap changed, the two size rows would test the wrong boundary silently (a raise is still caught by the `+ 1` rows as explained in R-02; a small lowering is not). The container-tests crate can depend on `tidewise-helper-protocol` only if the human accepts the dependency; otherwise add a unit test in the protocol crate that reads the constant from a fixture. Lowest priority.
6. **Wrong-summary safeguard:** rows whose request is valid and whose argv is the true summary are exactly the `start:` rows. If a start check were weakened they would run a real install in the container (the mutation did), and "nothing changed" fails them. That is the intended trip-wire and it works; the version rows and the protocol-version rows would also reach a job if their validation were dropped (their request keeps the true summary), and the same trip-wire fires. Real jobs there are harmless: container only, the dummy package.
7. **Baseline re-basing** (`packages_before = packages_now`, `files_before = files_now`): sound, one failing row is reported once; a later row that *also* changes the system is still reported because it is compared with the moved baseline. The only blind spot is two rows changing the system in cancelling ways, which is not plausible.
8. **Journal capture:** `FakeJournal` is a datagram socket at the real journal path, drained with `recv` after the process exit. It sees one datagram per `sendto`. It would **not** see an entry sent over `/dev/log`, the kernel log, or a memfd-passing large entry (the helper's entries are short, ASCII and capped). A refusal that also wrote an extra line to stderr or stdout is caught by the exact stderr and stdout checks.
Needs a human decision: no.

### R-08 (Low, CONFIRMED) The `gate` target mostly restates the implementation; a few things it cannot see
Where: `fuzz/fuzz_targets/gate.rs`, `fuzz/Cargo.toml`, `tests/fixtures/helper-gate/*`.

Checked against `crates/helper/src/{args,gate}.rs`:
- Cut semantics: sound. Byte 0 caps the argv text (0 to 255, further capped by what is left); byte 1 `% 16` caps the id text (0 to 15); `rest.split_at(len.min(rest.len()))` cannot panic; `data.get(2..).unwrap_or_default()` cannot panic. The only `expect` in the target (`a summary without a valid request`, line 78) is a helper promise (`Verdict.summary` is `Some` only for a request that passed), not a harness risk. Up to 15 uid characters means 11 to 15-character inputs exist, which are all `None` by the 10-digit cap: good for the "too long" path.
- `caller_uid`: the assertion `Some(n)` implies all ASCII digits and `n.to_string().trim_start_matches('0') == text.trim_start_matches('0')` holds for leading zeros (`007` gives 7) and for `0` (both sides empty). For 10-digit values above `u32::MAX` (`4294967296` to `9999999999`) the helper returns `None`, so nothing is asserted: correct. Weakness: the check is one-directional. A helper that returned `None` for **every** input would pass; the converse ("up to 10 digits that fit in a `u32` give `Some`") is not asserted. The unit tests cover it (`the_callers_identity_never_changes_the_answer`), the fuzz target adds only panic-freedom and "no non-digit becomes a number". No seed contains leading zeros, `+`, a 10-digit overflow or non-ASCII digits; the fuzzer has to find them (it will, cheaply).
- Accepted path: reachable. `accepted.bin` is `1a 03 | "update system (3 packages)" | "100" | request`, which gives `Decision::Accepted` (the summary depends on the count of the confirmed lines, not on names or versions, so mutations of names and versions keep it accepted). `summary-mismatch.bin` and `broken-request.bin` cover the other two arms. Good.
- Tautologies: `Accepted` asserts `text == summary(&accepted)` and `text.as_bytes() == argv_text`: both are `decide`'s own construction (`expected = summary(&request)`; `expected.as_bytes() == summary_arg`). `Refused` asserts `text == summary(&parsed)`: also construction. The assertions that can detect a real bug are: Accepted implies `parse_request(request).is_ok()`; a refusal's summary is printable ASCII and at most `MAX_SUMMARY_BYTES`; a refusal's summary never equals argv; `summary_arg` gives bytes back and refuses every other shape. These are true promises, not vacuous, but they are not independent of the code.
- The `request` fuzz target already covers `parse_request`; `gate` adds `summary_arg` and `caller_uid` panic-freedom and the combined path. Not in CI (documented). A clean 600 s run is still pending in the background job; I did not look at it.
Recommendation: add the converse assertion for `caller_uid` (digits only, `len <= 10`, value fits `u32` gives `Some`), and two seeds (`0000000007`, `4294967296`). Needs a human decision: no.
